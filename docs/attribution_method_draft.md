# 从真实披露构建可检验归因方法（草案 v0.1，2026-10-02）

## 范围与来源

开发案例：联想 FY2023Q3，截至 2022-12-31，公告文件 `data/raw/lenovo/FY23Q3_170220231201.pdf`。页码为 PDF 页码（本文件与印刷页码一致）。抽取文本、页面图片、数据库输入及计算公式存于 `docs/evidence/attribution_case/`。

本文件是在观察 Dell/HP 回放结果前制定的分析规则。它是交给 Agent 的方法草案，不包含评测题的标准答案。尚未修改运行中的 attribution skill、题库或现有根因标签。

## 从案例发现的三条分析路径

### 1. 需求疲弱、去库存与周转效率

披露 p2：PC 需求疲弱，渠道库存过剩，公司推动减少渠道库存；公司期末存货按季度及按年下降超过 9 亿美元。公司账面存货与渠道库存不同，不能用前者直接证明后者的余额。

因子：收入同比、存货同比/环比、COGS 同比、DIO 同比/环比、DSO/DPO/CCC、毛利率。DIO 用平均期初期末存货 / 单季 COGS × 实际季度天数。同比比较为相邻四个连续财季，跨公司同时报告季度起止和披露日期。

初步筛选分支（只生成假设，不直接证明经营因果）：

| 数据模式 | 假设/下一步 |
|---|---|
| 收入同比下降、存货同比上升、DIO 同比上升 | 库存压力候选；排查需求、备货、并购与口径，不能只靠三项指标确定需求下降 |
| 收入同比下降、存货同比下降、DIO 同比不降 | 存货在减少，但相对销售成本仍未显示周转改善；查需求下滑与调整滞后 |
| 收入同比下降、存货同比下降、DIO 同比下降 | 周转天数改善候选；查 DPO/DSO、现金流与披露，不直接称恢复增长 |
| 收入同比上升、存货同比上升、DIO 同比不升 | 与业务规模扩大相容；不能自动称异常或季节性 |
| 混合、不满足或数据缺失 | 保留不确定性，扩展证据/拒绝强制分类 |

连续至少两个期间同向作为持续性证据；用该公司目标期之前的同财季变化建立季节基线（不混用同比绝对差与环比变化率、不把当前点纳入基线）。不能用 2.5 个标准差作为真实事件的唯一准入门槛。阈值/分支此后修改必须记录方法版本并重新验证。

### 2. 总收入下降与业务结构变化

披露 p1–3：智能设备业务下降，基础设施和服务业务增长；p11 提供本期和上年同期分部收入与抵销。

使用真实分部数据，将各分部收入变化及抵销变化加总为集团收入变化：Δ集团 = ΣΔ分部 + Δ抵销。贡献率可超过 100% 或为负，这是其他业务对下降的抵消，不是计算错误。

这份 p11 是三个月分部表；另一处附注是九个月累计表，不得混用。现有 facts_detail 的地区/产品线由合成生成，不可用它证明真实分部原因；真实分部需单独入库、带来源和抵销行。HP/Dell 分部名字不同，先按各自真实结构计算，再映射到客户端设备/基础设施等可比类别；不能直接对齐名称。

### 3. 汇率影响与无法由现有财务因子识别的原因

披露 p2 提到货币兑换的负面影响。现有统一美元数据库没有恒定汇率收入、销量/均价或渠道销售数据，因此仅靠存货和收入无法分离汇率、价格、销量效应。

正确输出应区分：数据库计算事实；管理层披露的解释；与数据相容的推测；仍无法验证的部分。不将该汇率描述擅自解释成可与需求贡献简单相加的百分比，不补造 PVM 或渠道库存数字。

## 交给 Data Agent 的通用工作流程

1. 先明确问题、对象、季度、单位、as_of 和数据可得范围。
2. 计算方向、幅度、历史/季节基线与持续性，检查映射和重分类。
3. 生成至少一个候选解释和一个竞争解释；依据上表选择要取的因子，不预设公司或年份答案。
4. 用真实分部贡献、周转分解和同行相近覆盖期间比较，记录支持/矛盾/缺失证据。
5. 检索截至 as_of 已披露的公告/MD&A，返回文档、页码、原文位置和发布时间；先独立给数据侧判断，再核对披露。空 filing_notes 不等于公司没有披露。
6. 输出结构化事实与引用、候选原因及证据、不确定性。保留既有行业/公司/口径标签作为一个维度；经营事件类型另作为草案维度，不将“industry_wide”当成“需求下降已证实”。
7. 对每个数值绑定公司、期间、指标、口径、单位和结果行，护栏验证后提交；数据不足允许 abstain。

## 泛化性验证与回测设计

- 方法发现集：联想案例与其他开发期间。HP 用作开发验证；首轮 Dell 作为公司留出集。
- 本轮只做原始财务数值上的回放，检查计算可移植性与可能分支；没有独立 Dell/HP 披露标签，不报告准确率，也不是完成的 Agent 评测或预测回测。
- 正式验证须先建立公司×期间事件标注：来源、发布时间、事件类别、对应指标、支持/反驳证据、允许多原因及“无法判定”。标注不得由被测 Agent 自己生成并直接充当 gold。
- A 组只给财务数据：评价能发现哪些模式以及是否正确保留不确定性。B 组增加截至 as_of 的披露检索：评价证据检索、引用与结论支撑。两组分开评分，不能把阅读原文答案的收益当成数据推理收益。
- 基线 Agent 对比 +方法论 Agent，控制模型、工具、预算、题库相同；每题三次，指标包括事件/标签匹配、证据支撑率、无依据原因率、阴性误报率、拒答/覆盖率、延迟和 token。
- 每次依据 Dell 结果修改方法后，Dell 这部分变为开发集；保留另一些未查看的公司/时期最终测试，避免反复调参后仍声称盲测。评测事件有真实版本与披露日期，冻结 as_of 后不得用未来复苏或重述支持当时解释。
- 不擅自扩充正式题库；新增事件先放候选档案，正式题量及版本变更单独记录。每次失败写入“现象→证据→根因→方法改动→复测→回归”的档案。
