# FinSights 实验与 Query 分析看板设计与待办裁定

日期：2026-10-05。供用户按可用额度选择的开发执行模型实施。

## 1. 目标与范围

增加一个简单的本地看板：按实验查看全部 query、快速筛出系统可识别的 bad case，并进入单条问题查看答案、执行轨迹、查询和计算证据，以及自动过程指标。支持之后每轮几十条问题的优化实验。

本轮属于第一阶段的入口和可观测性完善。每个 query 每个版本运行一次，人工判断业务质量。复用 agent.cli、现有循环、五件套运行包和 review.md；现在可查看单条运行和已有批量结果，之后接入归因数据集。看板支持实验汇总不意味着现在构造数据集或启动大批量模型运行。

建议用 Streamlit 单页实现，增加一个轻量界面依赖；具体选型可以调整，不因此重写 Agent 框架。

## 2. 单页布局

信息层级为“实验列表 → 实验内全部 query → 选中 query 的详情”，仍在同一页面内完成。单 query 运行也作为一条记录的实验，不需要另一套页面。

```text
┌─────────────────────────────────────────────────────────┐
│ FinSights              实验 [选择 experiment] [刷新]     │
├─────────────────────────────────────────────────────────┤
│ 问题：[多行 query 输入框                              ]  │
│ [开始分析]  高级设置：截止日期 / 步数上限                 │
│ 解析范围：联想 · FY2023Q3 · 当前库                        │
├─────────────────────────────────────────────────────────┤
│ 本次实验：总题数｜已终止｜运行中｜红色 bad case｜token    │
│ [全部 / 仅 bad case / 待人工] [状态] [原因] [搜索 query]  │
│ 题号   query 摘要       状态     标记原因     耗时 token  │
│ Q01    存货是否改善…    已回答   待人工审阅    25s  …     │
│ Q02    应收变化原因…    拒答     🔴 步数耗尽   90s  …     │
│ Q03    毛利率变化…      已回答   🟡 修正后核验通过 …       │
│ 选中 Q02 → 以下显示该条详情                              │
│ 单条：状态｜耗时｜步数｜工具调用｜token｜异常             │
├────────────────────────────┬────────────────────────────┤
│ 答案与依据                 │ 执行时间线                 │
│ 完整 Markdown 答案         │ ① 系统提供初始数据         │
│ 数字核验状态               │ ② 模型 → query_metric      │
│ 业务质量：待人工审阅       │ ③ 工具返回 r2              │
│ [展开 claim 与来源]        │ ④ 核验打回 → 修正 → 回答   │
├────────────────────────────┴────────────────────────────┤
│ 选中事件详情：参数 / SQL / 结果表 / 错误反馈              │
│ [运行指标] [输入与配置] [运行包文件]                      │
└─────────────────────────────────────────────────────────┘
```

主体放实验选择、汇总指标、query 表和单条详情。SQL、结果表和配置默认折叠，点击事件或引用再展开。几十条 query 使用可排序表格，必要时分页；不一次加载所有完整 trace。不要增加复杂大屏或排行榜。

### 2.1 实验列表与 Query 表

实验选择项显示实验名、时间、代码版本、题量和状态。实验可以是一次手动 query、一次数据集评测或人工导入的一组历史运行；人工分组标明来源，不能伪装成同一配置执行的实验。

Query 表至少包含：query_id、问题摘要、运行状态、自动检查状态、bad case 原因、人工审阅状态、耗时、输入/输出 token。完整问题点击展开。默认保持题目顺序，支持按失败优先、耗时或 token 排序；支持搜索问题和筛选失败原因。

每次实验显示所有计划 query，包括尚未启动、执行中、已结束和缺失结果的条目，不能只列成功落盘的包。没有计划清单的旧实验只显示已知条目，并注明“计划总数未知”。

选择 query 后显示它原有的单条答案、trace、指标和来源；返回列表保留筛选条件。历史包缺答案或结果也保留该行，允许查看已有轨迹。

### 2.2 自动 bad case 标红规则

颜色必须同时配文字与原因标签，每个标签可点击定位 trace、核验反馈或评分记录。自动标记与人工审阅是两个独立字段。

| 显示 | 可识别条件 | 处理 |
|---|---|---|
| 🔴 运行异常 | API 重试后失败、进程异常退出、超时等有明确记录的终止错误 | 展示错误类型与终止证据 |
| 🔴 预算耗尽 | 最终因步数/token/时间预算终止 | 标明“未完成分析”，不把诚实拒答评价为编造 |
| 🔴 最终核验失败 | 最终 answered，但 verified=false 或明确终止于核验未通过 | 展示最终反馈和相关 claim/rid |
| 🔴 评分失败 | 后续有明确的确定性 grader 或已校准 judge 的失败记录 | 展示判分项、来源、规则版本；judge 判定注明“待人工复核” |
| 🔴 已知期望不符 | 后续数据集明确 expected_behavior，且实际行为被规则判为不符 | 引用标准和实际状态 |
| 🔴 记录不完整 | 任务已确认结束，但必需文件缺失、JSON 损坏或引用指向不存在的结果 | 标为记录问题，不能推断业务答案错误 |
| 🟡 过程警告 | 工具失败、核验打回、API 重试后最终恢复成功；结果截断 | 保留过程问题，默认不计入红色 bad case |
| 🟡 待人工判断 | 普通 clarify/refuse 没有已知期望，或有不同评分结论 | 不自动认定拒答不当 |
| 中性：未发现自动失败 | 正常回答且可用规则未报错 | 业务质量仍待人工，不显示“归因正确” |
| 中性：未完成 | 未启动、运行中、等待配额或尚未有终止信息 | 不按缺最终文件判失败 |

规则不得通过搜索回答中的“错误/拒答”等词直接判红。进行中的部分 trace 不视为损坏；没有心跳时不能仅因文件暂时未更新就判超时。预算终止、合法澄清和运行异常需要根据明确原因区分。

只按当前证据识别：没有 gold 或评分记录，不能自动判断业务归因、SQL 语义或经营解释正确。人工判为 bad case 的条目也可以标红，但标签写“人工确认”，保留来源，不冒充系统自动识别。不同规则同时命中时显示多个原因，每个 query 只计一次 bad case。

## 3. 交互

### 3.1 输入与执行

- 必填只有 query。高级设置仅 as_of 和 max_steps，默认取配置，显示实际生效值。
- 显示解析后的公司与期间，解析不到的字段标“未确定”，由原流程澄清。
- 初始包标“系统提供”，补充取数标“Agent 查询”，不把系统过滤算成模型自主取数。
- 被测路径继续禁用 get_filing_notes/search_disclosure，Agent 不接收经营解释正文。
- 只有点击“开始分析”启动新运行；页面刷新、重新渲染、选历史包都不能调用模型。
- 初始版本新增 query 仍按单任务执行，运行期间按钮禁用；实验浏览不受影响。以后批量执行复用现有 runner 与限流策略，不在看板里重写调度器。失败不自动重跑整题。
- 实时显示最近一步，如“正在查询指标”“等待模型”“API 重试等待”。不编造完成百分比。
- 历史入口按实验选择，实验内表格展示全部 query；单条旧包可登记为一个单题实验。浏览只读，不调用模型。
- 运行异常也能查看已取得的轨迹；旧包缺信息时显示“未记录”。

### 3.2 答案与证据

- 完整渲染 answer.md，显示 run_id、终止状态和核验结果。
- “核验通过”展示为“数字/引用规则通过”，不展示为“归因正确”。澄清、拒答时核验标“不适用”，避免 verified=true 被误读。
- claims 展示文本、数值、单位和 rid。点击 rid 定位工具结果，展开参数、SQL（如有）、结果行及来源。
- 截断结果明确标记，并提供已有回查方式，不把预览称为完整结果。
- 端到端质量、取数准确性、运行可靠性展示已有审阅结论，没有记录则“待人工审阅”。可读取人工审阅文件，不需要复杂编辑系统；自动失败标签与人工业务判断分别展示。

## 4. Trace 时间线

按真实事件顺序展示，同一个 step 允许多事件，不以 step 当唯一键。

| 事件 | 默认显示 | 展开内容 |
|---|---|---|
| 初始数据包 | 系统范围、行数、rid | 规则、参数、SQL、数据表 |
| 模型响应 | 步数、可见输出、提出的调用、耗时/token | 实际返回的正文与调用参数 |
| 工具结果 | 工具名、成功/失败、rid、耗时 | 参数、SQL、结果或错误 |
| 受阻调用 | 工具及阻止原因 | 守卫反馈 |
| 核验打回 | 次数、反馈摘要 | stop_reject 完整反馈 |
| API 重试 | 次数、错误、等待 | 已记录的客户端事件 |
| 压缩与召回 | 已记录的层级、rid | 原始事件详情 |
| 结束 | 已回答/待澄清/拒答/异常及原因 | final/result/run_meta |

没有可见推理输出时不生成“思考过程”，不要求隐藏思维链。开发者核对现有全部事件类型，未知类型折叠显示原记录，不静默丢弃。

## 5. 自动指标及口径

### 5.1 顶部卡片

| 指标 | 口径 |
|---|---|
| 状态 | 结合 final/result/run_meta 和进程退出；运行异常与正常拒答区分 |
| 总耗时 | 新运行记录接收提交至完成导出的单调时钟时长；旧 latency_s 标“原记录运行耗时”，不假定包含初始包和导出 |
| 模型步数 | 实际模型响应数量，与现有 steps 核对；初始数据包不算模型步数 |
| 数据工具调用 | 实际执行的工具事件计数，系统初始取数单列；不重复统计 assistant 调用与返回事件 |
| 输入/输出 token | 分别累计实际 usage；total_tokens 不再叠加。缺失显示“未返回/部分记录” |
| 异常 | 工具失败、受阻、API 错误分项计数；核验打回单列 |

### 5.2 展开指标

- 每种工具调用/成功/失败次数及耗时，标签为“执行成功情况”，不称“取数准确率”。
- 模型请求累计耗时、单次最大耗时、API 重试次数、有记录的退避等待。
- run_sql 失败次数；其他指标工具的查询或编译错误另列，不将 sql_errors=0 解释为全部查询无误。
- final_answer 提交次数、stop_reject 次数、最终核验状态。
- 实际记录的压缩、recall、受阻调用数量。
- 生效预算、已用步数/token；不预测任务完成比例。
- 初始包行数、结果条目数、截断条目数、无法定位结果的引用数。引用能定位不等于支持经营解释。

并行请求的累计耗时不能相加当作总耗时。未单独记录限流等待时显示“未单独记录”，不能用差值伪造精确等待。

费用默认“未获得实际计费信息”。若按配置单价估算，要标“参考价估算”，不称免费档实际支出。不显示无人工或标准答案依据的准确率。

### 5.3 实验汇总指标

实验顶部展示计划总数、已终止数、运行中/排队/未启动数、红色 bad case 数、过程警告数、已审阅数、累计输入/输出 token。bad case 可按运行、核验、评分和记录问题分组统计，同一 query 的总体计数去重。

以下比例必须显示分母和覆盖情况：

- 终止进度：已终止 / 计划总数，包含失败终止，不能命名“成功率”。
- 自动 bad case 比例：已终止 query 中标红数 / 已终止数，注明自动规则版本；缺少记录的查询不静默剔除。
- 已回答比例：answered / 已终止数，与核验状态分开。
- 回答核验通过比例：verified=true 的 answered 数 / 有已知核验结果的 answered 数，同时显示核验未知数。
- 评分通过比例：只在有评分记录时展示，通过数 / 有评分的已终止 query 数，并注明评分覆盖数 / 已终止数。

单条耗时可汇总平均值、中位数，注明样本数与缺失数；累计 token 标明缺失 usage 的条目数。实验总墙钟耗时来自实验自身开始/结束记录，不用各 query 耗时相加代替并行实验耗时。

之后用固定数据集对比版本时，保持 query_id 稳定，记录题集与数据版本。该版先支持浏览每轮全部条目；不强制新增复杂跨实验对比图。不能把不同题集、输入范围或评分规则的百分比直接当成优化收益。

## 6. 实现与记录补齐

### 6.1 实验索引

轻量增加实验 manifest/index，不复制所有 trace，也不迁移原运行包。每个实验至少保存：experiment_id、名称、来源、创建时间、代码与数据/配置版本、题集版本（若有）、计划 query 清单。每条包括稳定 query_id、原始问题或题目引用、运行状态和 run_id/package_path；查询编号与运行 ID 分开。

同一个 query 在下一轮优化实验中保留 query_id，新的运行获得新的 run_id。没有数据集的单题实验也使用同样结构。如果实验配置混合，应注明混合并保留逐条版本信息，不虚构统一版本。

优先适配 eval.runner 已有 summary 和 trace；旧批量结果没有完整五件套时展示已有指标与轨迹，并注明缺失，不自动补造或判业务失败。初始清单用于在失败或尚未启动时仍保留 query 行，索引随任务状态更新。

列表只读取小型元数据和评分摘要，选中一行才加载完整 trace/results。评分内容放在评测或展示侧，不因索引中有 gold 引用就交给 Agent。自动标记保留规则 ID、原因、证据定位和规则版本；人工审阅单独存放，刷新不覆盖。

### 6.2 单条执行与记录

建议页面启动现有 CLI 的后台任务，使用同一已分配的 run_id 与目录，界面读取运行状态和 trace。命令使用参数数组，不将 query 拼接为 shell 代码。

开始前建立目录，逐行写 trace.jsonl，结束或异常时导出其他文件。如当前只在结束时导出 trace，应补齐写入时点。前端约每 1–2 秒只读刷新；读取末尾未写完的一行时等待下一次，不把整包判坏。页面关闭不自动启动新任务，重新打开可查询原任务状态。

优先补齐：事件序号与时间戳、开始/结束/终止原因、初始包事件与 rid、实际预算与禁用工具。已有 SQL/结果通过 rid 关联，不重复造存储。只显示实际存在的信息。

旧 run_meta 的脱敏规则误遮盖 max_tokens、压缩 token 阈值等非密钥配置。调整为按秘密字段语义脱敏，保留 API key 等凭证保护，允许显示非敏感预算；旧包不反推被遮盖的配置。

新运行明确记录时区，历史时间缺时区时原样显示并标“时区未记录”。默认本机监听，不做托管、登录或上传，也不显示 .env 内容。

## 7. 交付检查

先用现有包开发界面，不消耗 API 额度：

- runs/cli-20261005-135811：惠普取数，answered、verified=true，包含一次核验打回。
- runs/cli-20261004-191242：步数耗尽拒答。
- runs/cli-20261004-192151：429 配额错误留下的部分包。

它们用于界面检查，不形成新数据集，不重跑这些题。今天的成功包记录旧 commit 与 dirty，初始包事件缺失时显示“未记录”，不能补造历史 trace。

再用现有批量实验的 summary/trace 检查看板能列出本次全部已知 query，筛出失败并进入详情；未记录计划清单时明确总数未知。用离线界面样例检查排队、运行中、未评分、恢复成功、最终核验失败和缺失记录的标色，不发起新的批量 API 运行，也不构造业务评测数据集。

验收重点：实验分组与 query 映射正确；失败有明确原因和证据；正常澄清或恢复后的调用错误不被一概标红；无评分不显示业务准确率；几十条列表切换后能定位原始运行，刷新不重复执行 query。

交付实际启动命令、截图或本地页面、指标口径、兼容情况和缺失项。配额恢复后补跑一次联想验收 query，检查界面到 CLI 到运行包的链路。
