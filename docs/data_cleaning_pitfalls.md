## 一、联想 PDF（港交所披露易）

### 1. 标题搜索永远 0 结果

- **现象**：`titleSearchServlet.do` 用 `title=RESULTS ANNOUNCEMENT`、`title=業績公告` 都是 0 条；去掉标题按日期窗口查，同一窗口却有 74 条公告。
- **根因**：联想公告的实际标题是"二零一七/一八年財政年度第一季業績公**佈**"——"公佈"不是"公告"；英文标题是"RESULTS ANNOUNCEMENT"但接口的 title 匹配行为与直觉不符（大小写/分词不可靠）。
- **解法**：不信任服务端标题过滤。按**财年窗口**（7/1 至次年 6/30，`t1code=-2` 全类别）拉全量公告，本地正则 `(第一季|中期|第三季|全年)業績公佈` 过滤，每财年恰好命中 4 份（Q1/中期/Q3/全年）。10 个财年窗口共 37 份，与理论值（2017Q2–2026Q2 = 37 个季度）吻合。
- **代码**：`etl/fetch_lenovo.py` 的 `search_window()` / `TITLE_RE`。
- **附带**：stockId 是港交所内部 id（00992 → **2325**），需先调 `prefix.do` 查得，不能拿股票代码直接搜。

### 2. 文件名冒号 → NTFS 备用数据流（最隐蔽的一个）

- **现象**：下载"成功"、`write_bytes` 不报错、文件也"存在"——但 37 个 PDF **全部 0 字节**。文件名显示为 `FY18Q1_18082017 07`（在冒号处截断）。
- **根因**：manifest 日期含时间（`18/08/2017 07:59`），拼进文件名后 Windows 把 `07:59.pdf` 解释为文件 `FY18Q1_18082017 07` 的 **NTFS 备用数据流（Alternate Data Stream）**——写入的内容进了流，主文件保持 0 字节。Git Bash 的 `ls` 和 Python 的 `os.path.exists` 都不会报错。
- **解法**：文件名清洗 `re.sub(r'[^0-9]', '', date)`（`18/08/2017 07:59` → `180820170759`）；manifest 里保留 sha256，下载后校验。
- **教训**：**下载类脚本必须校验产物字节数/哈希**，"没抛异常"不等于"写成功了"。

### 3. 兼容码位字符：肉眼相同、码点不同

- **现象**：资产负债表里"現金及現金等價物"行始终匹配不上映射键（其他行都正常），被旧逻辑误判成小计行，引发一连串组件闭合校验失败。repr 打印发现该行是 `'現 金及現金等價物'`——中间有个空格。
- **根因**：PDF 内嵌字体的 cmap 把"金"映射到了**兼容码位**（U+FA68 金，KS X 1001 兼容区），pdfplumber 提取时该字形与相邻字符间产生空格，且字符码点与常用"金"（U+91D1）不同——字符串比较必然失败。
- **解法**：PDF 文本与 YAML 映射键**双侧做 `unicodedata.normalize("NFKC")`**（NFKC 会把 U+FA68 折叠为 U+91D1），标签匹配前再去掉全部空白。
- **代码**：`extract_lenovo.py` 的 `_nfkc_all()` / `_load_map()`。
- **教训**：中文 PDF 抽取的字符串匹配，**先 NFKC 再比较**应成为默认习惯；repr 能看见但肉眼看不出码点差异。

### 4. 报表行的七类解析子坑（同一个 90 行函数里全遇上了）

以"一行 = 标签 + 附註号 + N 个数值列"为模型，坑依次是：

| 子坑 | 例子 | 解法 |
|---|---|---|
| ① 附註号形态多 | `7(a)`、`9(a)(iii)`、`11(a)(ii),12(b)`（复合 + 中文逗号 NFKC 后变半角逗号）、纯数字 `12` | 附註判定 = "以数字开头且含字母"；纯数字 1–2 位的尾部 token 一律视为附註剥离（值列 ≥4 位必有逗号，不会误伤） |
| ② 括号负数 | `(212,900)`（权益中的认沽期权）、`(8,647,602)`（銷售成本） | `(…)` → 负号；銷售成本取绝对值入库（成本以正数幅度存储） |
| ③ 破折号占位 | `可供出售金融資產 - 373,077`（当期为零） | `-`/`–`/`—` 视为 None 值位，参与列计数，防止列错位 |
| ④ 标签跨行 | `以公允值計量且其變動計入其他全面收益的` / `金融資產 64,572 84,796`；`總負債` / `39,115,743 34,380,098`（**合计标签单独成行**） | 无数值的行进 pending 缓冲，与下一行标签拼接后再查映射 |
| ⑤ 数字内部断字 | `6,052,716 4,810,75 1`（第二个值的末位被空格切开） | 窄正则只拼接"逗号后 1–2 位 + 空格 + 1–2 位尾巴"的碎片（`(\d,\d{1,2}) (?=\d{1,2}(?![\d,]))`）——宽了会把两个值连起来 |
| ⑥ 数字内空格 | `銷 售成本 (13,119,563 ) (35,655,611 )`（空格把括号拆断，词法全乱） | 弃用逐 token 扫描，改为正则扫描器 `\(\s*-?[\d,]+\s*\)|…`（容忍括号内空格）+ 负向断言 `(?<![\d,.])[\d,]+(?![\d,])` 防止把 `13,119` 切成 `3,119` |
| ⑦ 页脚页码 | 每页末尾孤立的 `13`、`14` | 跳过纯 1–3 位数字的行 |

- **代码**：`extract_lenovo.py` 的 `VAL_RE` / `_to_num()` / `_split_line()` / `_parse_bs_pages()`。
- **教训**：财报 PDF 的"一行"不可信，**解析单位应该是"值 token 的位置关系"而不是空格分词**；每个修复都要用"修复 1 个、回归全部 37 份"的方式验证——本案例中先后迭代 8 轮才做到 0 校验问题。

### 5. 损益表列数不固定 + 年报表头不写期间

- **现象/根因**：Q1/Q3 损益表 2 列（本期三個月、上年同期三個月）；**Q2 中期 4 列**（本期三個月、本期六個月、上年三個月、上年六個月）——第一列即单季，Q2 无需倒算；Q4 年报 2 列且**表头只写"二零一八年"**，不出现"止十二個月"。
- **两个子坑**：列数正则最初只数"止三個月/六個月/十二個月"，漏了 **"止九個月"**（Q3 公告是三個月+九個月各 2 列）→ `n_cols=2` → 后两列被吞进标签（`收入212,938,53234,711,634`）；period_type 曾试图从表头判断 12m → 年报永远判成 3m → **全年值被当单季写入 Q4**（Lenovo FY18Q4 revenue 45,349.943 百万美元的荒唐值）。
- **解法**：`n_cols = len(re.findall(r"止[一二三四五六七八九十百]+個月", header))`；`period_type` 不看表头，**按公告类型判定**（Q4 公告的损益表 = 全年 12m，其余 = 3m）。
- **教训**：能从**外部结构**（公告类型）推导的属性，不要从**内容**（表头措辞）猜。

### 6. 页面顺序不固定 + 母公司副本

- **现象**：FY18Q1 资产负债表在 p13–14，FY18Q3 的损益表（p13–14）却在资产负债表（p15–16）**前面**；几乎所有公告 p19–20 还有第二套"綜合資產負債表"（母公司口径）。
- **解法**：不做页序假设，逐页扫描取**第一处**"綜合資產負債表"（= 合并口径）及其"(續)"页；小节状态机：资产页 `非流動資產 → 流動資產`，續页从"股本"行起默认 `權益`（该小节无标题行），遇 `非流動負債`/`流動負債` 标题切换。
- **代码**：`_find_pages()` / `_parse_bs_pages()`。

### 7. 科目行名九年漂移（含简写变体）

- **现象**：抽取脚本输出"未映射行"清单，9 年间累计出现：`可供出售金融資產` → `以公允價值計量且其變動計入損益的金融資產` → `以公允**值**計量…`（"價"简写成"值"！）；`應收貿易賬款` → `應收貿易賬款及票據` → `應收貿易賬款、租賃款及票據`；`衍生金融負債` 从流动负债小节挪到非流动负债小节。
- **解法**：映射表允许多变体共存（都指向同一标准科目）；新增行的发现机制就是**抽取校验本身**——未映射行全部落警告，人工逐个定映射后重跑，直到 0 警告。
- **代码**：`account_map.yaml` 的 `lenovo_bs_sections`；`extract_lenovo.py` 的 warnings 收集。

### 8. 同名行跨小节歧义

- **现象**："貸款"在非流动负债（→ long_term_debt）和流动负债（→ short_term_debt）各出现一次；"遞延收益"同理（→ other_noncurrent_liabilities / deferred_revenue_current）。
- **解法**：映射表按**小节**组织（`lenovo_bs_sections`），解析器维护小节状态机，同名行按所在小节查不同映射。
- **教训**：账科目映射键必须是 **(小节, 行名)** 二元组，只有行名一级迟早踩雷。

### 9. 权益结构映射决策

- **结构**：總權益 = 股本 + 儲備 + 永續證券 + 其他非控制性權益 − 向非控制性權益簽出認沽期權。
- **决策**：`total_equity` 直接取报表"總權益"合计行（含 NCI，符合附录 A 口径）；`noncontrolling_interest` = 其他非控制性權益 + 認沽期權（负值）**两条求和**；股本/儲備/永續證券进 `lenovo_bs_ignored`（不映射、不告警），父项权益部分无标准科目、由恒等式间接约束。

### 10. 联想口径备注

- 单位**千美元**（CSV 忠实保留原值，入库时 /1000 → 百万美元，便于 V1.17 人工对数）；
- 應付票據（供应链金融票据）→ other_current_liabilities，`accounts_payable` 只含應付貿易賬款——与联想自身 DPO 口径一致（`account_map.yaml` 注释 1–5 条）。

## 二、SEC companyfacts（HP / Dell）

### 11. 扩展标签与维度事实：companyfacts 的结构性盲区

- **现象**：Dell FY2024 Q2/Q3（期末 2023-08-04 / 2023-11-03）的 `AccountsReceivableNetCurrent`、`AccountsPayableCurrent` 在 companyfacts 中**恰好缺这两个期末**（该标签 41 个期末中只缺这 2 个）；但对应 10-Q 的 R2 报表文件里明明出现 `us-gaap_AccountsReceivableNetCurrent`。
- **根因**：companyfacts 只收录**无非维度上下文**的标准分类账事实。这两份 10-Q 的该行要么挂了维度（segment context），要么用了公司扩展标签——两类都进不了 companyfacts，且 FY25 文件的比较期也没有重述。
- **解法**：4 条缺口按 verify 0.3 规则走 BLOCKED（questions.md Q4），选项是人工抄数（走 data/manual，V1.16 可溯源）或接受残差吸收（勾稽已闭合）。**教训**：companyfacts 适合做覆盖面，但**做完整性断言前必须先弄清它的收录规则**——"标签存在"与"事实被收录"是两回事。

### 12. 同一概念随年份换标签：回退 vs 求和（本阶段最重要的机制设计）

同一标准科目在不同年份由不同 XBRL 标签报送，两类情况**必须区分**：

| 情形 | 例子 | 机制 |
|---|---|---|
| 新旧标签**互斥**（同一时期只用其一） | HP 权益：早年 `StockholdersEquity`，后来 `StockholdersEquityIncludingPortionAttributableToNoncontrollingInterest`；HP 长期债务：FY17–FY22Q3 用 `LongTermDebtAndCapitalLeaseObligations`（23 个期末），之后 `LongTermDebtNoncurrent`（28 个期末），**重叠 12 个季度**；递延收入：post-ASC606 `ContractWithCustomerLiabilityCurrent` vs 早年 `DeferredRevenueCurrent` | **回退（fallback）**：主标签缺失才启用次标签，绝不求和——HP 两套长期债务标签在重叠期若求和会**翻倍** |
| 多标签是**组成部分** | Dell 短期债务 = `DebtCurrent`（Dell 不用 ShortTermBorrowings）+ `LongTermDebtCurrent` + `CommercialPaper`；Dell total_equity = `StockholdersEquityIncluding…` + 夹层 `TemporaryEquityCarryingAmountAttributableToParent` | **求和合并（sum-merge）**：value 相加、available_date 取最早、source_ref 连接 |

- **代码**：`account_map.yaml` 的 `xbrl_tags` / `xbrl_fallback_tags`；`load_db.py` 的 `_merge_facts()` 与 fallback 发射段（fallback 事实只在主标签完全缺失时发射，先于 merge）。
- **教训**：**"同一科目多个标签"必须逐对判断是同义还是部分**，这个判断只能结合各年 10-K 的实际列报做，不能自动猜。

### 13. Dell 可赎回 NCI 列于夹层：A = L + E 恒等式破裂

- **现象**：Dell FY2019–FY2021 约 8 个期间 `A − L − E` 差 0.7%–1.1%（超 0.5% 容差），例如 FY2019Q4：A=111,820、L=111,566、E=−942，差额 1,196。
- **根因**：Dell 把**可赎回少数股东权益**（redeemable NCI，临时权益）列在负债与权益之间的夹层，会计恒等式实为 `A = L + 临时权益 + E`；us-gaap 标签为 `TemporaryEquityCarryingAmountAttributableToParent`。
- **解法**：把该标签并入 total_equity（求和合并），使 `total_equity = 全部权益（含可赎回 NCI）`，恒等式精确闭合；口径写入 account_map 注释与 questions.md Q6。
- **教训**：勾稽检查失败不一定是数据错误，**先弄清公司的列报结构**再动数据。

### 14. 52/53 周财年的季度定位：月差公式系统性错位

- **现象**：Dell FY2026Q2（期末 2025-08-01）被定位成 Q3；FY2020Q3（期末 2019-11-01）占据了 Q4 槽位，把真正的 Q4（2020-01-31，15 个科目支撑的真期末）挤出了 periods 表，其下 15 条事实全部丢失。
- **根因**：`(pe.year − prev.year)*12 + (pe.month − prev.month)` 的月差忽略"日在月中的位置"——2025-08-01 距 2025-01-30 实际 183 天 ≈ 6 个月，公式算出 7 → `q = (7+2)//3 = 3`。
- **解法**：**天数法**：`q = max(1, round((pe − prev).days / (365.25/4)))`；财年末锚 = 年报 duration（360–371 天）的期末日集合；`|pe − anchor| ≤ 5 天` 判 Q4。
- **代码**：`load_db.py` 的 `fiscal_quarter()`（tests/test_etl.py 有 Dell/HP 真实例子的单元测试）。

### 15. 最新财年没有财年锚 + 杂散 instant 冒充期末

- **现象 A**：HP FY2026 Q1–Q3（2026 年 1/4/7 月末）整批丢失——它们的财年末（2026-10-31）的 10-K 还没披露，锚集合里没有未来锚。
- **解法 A**：**隐含锚** = 最后一个真实锚 + 1 年（52/53 周漂移 ±数日，可接受）。
- **现象 B**：某 instant 落在 2017-11-01（Dell/HP 财年开始日附近），仅 1 个科目支撑，却占据了 (FY18,Q1) 槽位，把 2018-01-31 的 11 条真事实挤掉。
- **解法 B**：候选期末日要求 **≥5 个科目支撑**（真资产负债表日有 15+ 科目）；同 (fy,q) 冲突取支撑多者。
- **教训**： periods 表是所有下游事实的连接键，**它的构造错误是放大器**——一个错误定位会静默丢掉十几条事实。V1.4/V1.5 的连续性检查能在最后兜底，但定位最好在源头做对。

### 16. Q4 倒算撞上时间窗口

- **现象**：Dell FY2017Q4 的 revenue/cogs 无法生成。
- **根因**：Q4 = 全年 − Q1 − Q2 − Q3，但 Dell FY2017 的 Q1–Q3 期末都在 2017-01-01 之前，按 plan"2017 年起"的窗口规则未入库 → 倒算缺输入。
- **处置**：接受缺口（2 条），questions.md Q4 留档。**教训**：窗口规则与倒算规则在边界期会互相作用，设计期就该想到"窗口内第一个 Q4 的三个兄弟季度可能在窗外"。

### 17. 年报聚合值漏进季度表

- **现象**：facts 表出现 (Dell, FY2026Q4, revenue) = 113,538（全年数）——V1.10 的单位检查（预期季度营收 5,000–40,000 百万美元）被击穿。
- **根因**：SEC 的年报 duration 事实（360–371 天）与 Q4 期末对齐后存成了 (fy, 4) 的普通事实。
- **解法**：FY 聚合值**只用于 Q4 倒算的输入，不入库**（`_kind` 内部标记，insert 前过滤）。

### 18. 公司报送毛利 ≠ 收入 − 成本

- **现象**：Dell 多个期间 `GrossProfit` 标签值与 `Revenues − CostOfRevenue` 不一致（不同年份两套收入标签口径混杂）。
- **解法**：**SEC 毛利一律派生**（`gross_profit = revenue − cogs`，is_derived=TRUE，source_ref 记录两个输入事实），映射表删除 GrossProfit；联想保留报表"毛利"行原文。口径决策记 questions.md Q6。

## 三、建库与校验层

### 19. 负权益下的"子项 ≤ 合计"检查不成立

- **现象**：Dell FY2019–21 报"|NCI| > total_equity"——如 FY19Q4：total_equity = 254（母公司 −4,569 + NCI 4,823），NCI 4,823 > 254。
- **根因**：母公司权益为负时，"子项 ≤ 合计"在数学上就不成立（合计 = 负的父项 + 正的子项）。
- **解法**：删除该检查（`check_identities.py` 注释说明了原因）；NCI 的正确性由 A = L + E 恒等式与公司报送口径保证。**教训**：为恒等式设计的健全性检查自身也要考虑符号域。

### 20. 比较期补报：available_date 偏晚 5–13 个月（20 条）

- **现象**：HP FY17Q4 权益、Dell FY18 各季营收等 20 条 original 事实，其首次 available_date 来自 5–13 个月后的后续申报的比较期（如 HP FY17Q4 权益最早见于 FY18 10-K，filed 2018-12-13）。
- **影响评估**：对 P6 的 as_of 隔离是**保守方向**（系统认为数据比实际更晚可用 → 快照少给数据，不会泄露）；不影响勾稽。
- **处置**：V1.14 记 BLOCKED，建议人工确认"比较期补报"加入例外（questions.md 附于 Q4 同节说明）。

### 21. 吸收项 5% 上限的正确语义

- **现象**：Dell 大量期间 other_noncurrent_liabilities ≈ 15–17%总资产。
- **根因**：Dell 并购 EMC 后递延所得税、经营租赁等真实巨大，**不是映射错误**（补齐 DebtCurrent/AccruedLiabilitiesCurrent/ContractWithCustomerLiabilityCurrent 后已大幅缩小）。
- **解法**：check_identities 把"吸收项 >5%"从**失败**降级为**报告项**（plan V1.8 的原文语义就是"超过的列入 questions.md"由人工判断），identity_report.md 输出全量清单。

### 22. 联想小计行必须映射进标准科目

- **现象**：identity check 报 Lenovo 各期 total_current_assets 缺失。
- **根因**：抽取脚本把"流動資產小计"行存为 `_subtotal_流動資產`，load 时被一刀切跳过。
- **解法**：`_subtotal_流動資產 → total_current_assets`、`_subtotal_流動負債 → total_current_liabilities` 映射（非流动小节无对应标准科目，继续跳过）。

## 四、工程与流程坑（简）

23. **git 工作流**：在临时分支上 `git add -A` 会把未提交 WIP 一起卷进提交，切回 main 即"丢失"——本例靠 `git reflog` 找回孤儿提交后按文件精确恢复。教训：自测类分支操作前先提交/暂存 WIP。
24. **G-selftest 的价值**：在临时分支故意埋违规验证检查正则，当场抓出 `api_key=` 字面量模式对测试假 key 的误报（检查不动，改测试写法）。
25. **HTTP 客户端的代理陷阱**：本机 7890 端口有代理服务，httpx 会走系统代理设置连接被拒而 curl 直连成功（或反之）；GitHub 推送间歇被重置时用 `git -c http.proxy=…` 一次性借道（不落配置）。抓数据脚本要允许逐请求降级重试。
