# 回答二：正式上下文压缩配置与实现顺序

2026-10-02 用户确认交给 GLM 5.3 开发。下列数值是待对照验证的起始方案，不是已证明最优参数。本次只写文档，尚未改 config、代码或验收结果。

## 裁定与原因

正式模型容量和工作上下文分别管理：保留当前配置 window=512000，并复核接口限制；16K 留作 V4.44 压力测试，不作为正式业务窗口。累计运行预算 500000 是各次 API 输入+输出之和，与一次调用容量不同。

现有正式 L3 约 246K 触发、L4/L5 479K 触发偏晚，可能在压缩前先耗尽累计预算。压力测试却以 2K 触发 L4/L5，最新失败包含 recall 29 次、L4 32 次；支持过早/过频压缩与工作证据保留不足的假设，但未证明 16K 一定装不下，也未排除模型循环或账本缺失。

采用“完整资料留外部、关键工作证据常驻、其他内容按需召回、旧历史整理为结构化账本”的范式。相关参考：[Anthropic 上下文工程](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)、[Claude 上下文编辑](https://platform.claude.com/docs/en/build-with-claude/context-editing)。特定产品的默认阈值不能直接证明 Agnes 的最佳阈值。

## 步骤 1：先修 token 计量和输出约束

修改 `agent/context.py` 及工具预览的计量，不能继续把中文、JSON、SQL 一律按字符数/4 当成可靠 token。优先使用适配运行模型的 tokenizer；不可得时，按内容类型估算并与每次 API `usage.prompt_tokens` 校准，保留误差及安全余量。工具定义、system、消息及工具调用参数均计入；与计费累计值区别记录。

trace 记录估算输入、实际输入、偏差、工具定义占用、各层压缩前后大小；压缩调用本身的 token/时间也纳入任务预算并验证现有计账是否完整。不得用另一模型 tokenizer 的结果宣称精确计量。

`agent/llm.py` 当前未传输出上限。核实 Agnes 端点实际支持的输出限制字段，显式配置并做能力探针；初始主循环上限建议 8000、摘要上限 4000，按任务表现调整。reserve_output=20000 暂时保留为本地余量，它不等于 API 输出限制。参数不支持时记录探针证据，不能盲目照搬其他接口字段。

## 步骤 2：保护当前证据，避免反复召回

先实现活动工作集，再调阈值。保留 system、原始任务、已加载必要 skill、未解决核验反馈、当前假设/竞争解释和关键数据口径。

为正在使用的 rid/披露 chunk 建立显式保护集合：来源为当前分析任务依赖、待核验 claims、未解决假设，以及最近召回/引用的证据。默认先保留最近 6 个完整结果与 4 轮交互，但活动依赖优先于单纯最近顺序。分支完成且已形成可核验账本后才释放保护；同时记录理由，防止永久保护全部历史。

检查当前 `CompState.stubbed` 的永久存根行为：已压缩 rid 再召回后，活动证据须能重新完整进入视图，不能立即重新变成同一存根。保留完整结果于 ResultStore，历史不改写，原引用可召回，assistant/tool 的协议轮次不拆散。

L4 投影也须保留活动证据：不能只让 L3 保护 rid，再被 L4 删除对应旧轮次。可在账本旁重注入有界证据块，包含必要数值/单位/期间、原文出处、支持/矛盾及未完成事项。按结果 ID 去重并记录依赖，不无界复制旧历史。普通财报只检索相关段落/表格，不整份灌入。

## 步骤 3：实现并试运行正式起始参数

| 参数/行为 | 当前 | 候选起点 |
|---|---:|---:|
| window | 512000 | 保持 |
| reserve_output | 20000 | 暂时保持 |
| L3 轻清理触发 | 246000 | 64000 |
| clear_at_least | 8000 | 保持 |
| L4 compact_threshold | 479000 | 128000 |
| stub_keep_last | 3 | 6 |
| ledger_keep_recent_turns | 2 | 4 |
| result_max_tokens / rows | 2000 / 50 | 暂时保持 |
| L4 压缩后目标 | 无独立参数 | 优先 80000，视证据可降至 64000 |
| 正式 l5_enabled | true | 先 false；L5 单独实验验证 |

建议新增显式 `l3_trigger_tokens=64000` 与 `compact_target_tokens=80000`，减少阈值与模型容量耦合；注册配置校验并记录 plan 变更，不能只写不存在的键。若先沿用旧接口，`l3_ratio=64000/(512000−20000)≈0.1300813`；两种方式择一，明确优先级，避免双重触发语义。

触发值与回落目标分开，只有能有效释放时才批量清理；相同 cut/相同内容不重复触发。保护证据后达不到目标时记录实际大小和原因，不强行删掉关键数据。若超过安全窗口，先缩小工具输出/转移已完成分支；仍无法满足时明确拒答并保存进展。保留原超长兜底，但也验证它不会静默丢失当前用户任务。

L5 暂不作为正式业务默认路径，但现有实现及测试保留；16K 压力测试继续覆盖 L5，不能通过关闭它冒充原测试通过。以后启用须验证摘要对数值、引用、竞争解释和未完成事项的保真度。

## 步骤 4：离线验证后，再跑真实对照

离线测试覆盖：中文/工具定义计量与估算误差处理；保护很早的活动证据；召回已存根 rid 后可读；L4 保留依赖；完成分支可释放；引用与 tool_call_id 不变；回落目标不引发连续重复压缩；关键反馈不丢；异常和预算诚实终止。沿用 plan 原有不变量；需要增加/调整检查项先登记，本说明不删除旧检查。

真实业务对照固定运行模型、问题、数据、工具、max_steps=20、累计预算和时间预算；比较原正式配置与新候选配置。问题覆盖普通查询、联想库存/DIO 长归因、真实分部抵销、多公司比较、需要披露检索的事件，以及大结果触发的长任务。每题三次，保存独立配置与 trace；普通题未触发压缩就如实报告，不能用它证明压缩有效。

报告最终核验/证据支撑与完成率、重复查询/重复召回、各层触发次数、最大实际输入、总输入/输出/压缩 token、步数、耗时、计量偏差。首先要求不丢关键证据、不放宽 verifier；再看是否减少循环及预算耗尽。不能把 token 减少但正确性下降写成优化成功。

若反复召回同一证据，先查保护/账本；证据需求确实超出目标再逐步提高阈值。参数无稳定收益则保留旧正式配置并记录结果，不按方案批准自动宣称优化完成。

## 步骤 5：V4.44 压力测试单独处理

用户授权先测工作集，再分别调整触发与保留策略；不增加步数作为第一选择。保留原题、window=16000、max_steps=40、原 verifier 和三项通过条件。独立测试文件/config，禁止覆盖旧失败证据。

按顺序对照：①原失败配置；②仅调整触发，初始可试 L3=8000、L4=11000、回落目标=8000，reserve_output=3000；③在②上加入活动证据保护与可召回恢复，再按 16K 容量选择保留量。上述压力参数也是候选，先测常驻 prompt/工具与证据大小，留计量余量，不照抄正式 6 结果/4 轮导致超窗。

逐项记录是否真实发生 L3、无 API 报错、最终答案通过 verifier，以及召回/压缩次数、进展和预算。未满足任何一项仍为 FAIL；正式业务成功不能替代 V4.44 PASS，也不自动解除既有 P4 阶段门禁。若需改变阶段门禁，另外提交具体证据供用户裁定。
