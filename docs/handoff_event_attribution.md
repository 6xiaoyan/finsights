# 回答一：从公开财报发现大事件并形成可验证的归因方法

2026-10-02 用户确认，供 GLM 5.3 执行。方案获批；开发与验收尚未完成。入口见 `docs/solution.md`。先完成 P4 已有修复与复核，再按 plan 推进 P5；可以先准备本方案的公开材料与候选档案。

## 目标与边界

解决 Q11 的事件发现问题，并建立“指标组合→候选解释→证据核对→有边界结论”的方法。采用数据驱动、披露驱动两条入口，不能只靠 z 阈值。财报用来发现与验证真实事件，不保证每个经营事件都能从现有因子唯一推出。

区分三件事：确定性数学分解、管理层披露的经营解释、尚待证实的假设。这里的回测首先是历史事件解释回放，不能宣称为事件预测或因果识别。

## 步骤 1：登记设计，修复数据候选口径

先读 `prd.md`、`plan.md`、`verify.md`、`docs/questions.md`、`docs/attribution_method_draft.md` 和 `docs/attribution_case_lenovo.md`。新增接口、表或评测维度先记 plan 第 12 节；正式题库数量不自动增加。

检查 `eval/generators/inject.py` 与 `fincalc.calc.seasonal_baseline`，统一定义并复用计算：

- 环比：本财季与上一连续财季；Q4 前期是同财年 Q3，Q1 前期才是上财年 Q4。
- 同比：与四个连续财季之前比较。所有比较保留真实起止日期，不以不同公司的同名财季推定同一自然期间。
- 季节基线：目标期之前、同财季的历史变化；排除目标点与未来点，明确用变化率还是绝对差、标准差 ddof、历史样本数。
- 样本不足、标准差为零或口径不可比：显式返回不可计算原因，允许用幅度/历史排名给线索，不能补造 z。

旧生成器混用了同比绝对差和环比基线；“n≤8 导致 2.5 永远不可达”不能直接解释当前实现。已有 |z|>2.0 两条候选只作为历史线索。先修公式、再生成候选，数学阈值不再是事件唯一准入条件。

离线验证须覆盖 Q4/Q1 边界、当前点不进入基线、两种变化口径不混用、少样本/零方差，以及重述与分拆的不可比情况。

## 步骤 2：建立公开披露索引和可引用正文

先用已有联想财报，随后补 HP/Dell 公开业绩公告及 SEC 10-Q/10-K 的 MD&A、财务附注。SEC companyfacts/submissions 只有数字与索引，不能视为已取得经营解释正文。优先发行人官网、交易所、SEC；新闻先作线索，再核对原始披露。招股书仅在相关业务变化需要时补充。

每份材料保存：公司、document_id、文档类型、财季/实际起止、published_at、source_url 或已有本地来源、原文件路径、SHA256、提取方式。无法确认发布时间的材料标记缺失，不用于严格 as_of 评测。

提取正文并按页/章节/表格切块，保存 chunk_id、PDF 页码与印刷页码、章节、原文位置。表格保留单位、列头、三个月/累计期间和抵销行；扫描页需要 OCR 后人工核对关键数字。原始文件保持不变。

实现公开披露检索工具：输入 company、period、query、as_of、top_k；输出引用 ID、文档与页码/章节、发布时间、原文片段和可继续读取的引用。历史评测只能返回 published_at≤as_of 的材料。不要把整份 PDF 塞进每步上下文，也不要把评测 gold 混入检索库。

财务数字也需版本/as_of 过滤：只过滤正文仍可能泄漏未来重述。现有 original/restated 如果无法代表当时可得版本，应把运行标为“当前数据库历史回放”，不得标为严格时点回测。

建议新增披露索引/检索模块与离线夹具，具体路径按仓库现有结构确定并在 plan 登记。

## 步骤 3：由披露主动找大事件

先读管理层业绩讨论，再读分部表、现金流、重大事项与附注。可以先做关键词定位，再通读相关上下文。寻找的事件包括：需求或渠道去库存、业务结构转移、汇率、减值/重组、并购/出售/分拆、重大订单或客户变化、供应中断、会计重分类等。该列表用于提示检索，不能当硬编码原因答案。

事件重要性看披露强调程度、经营范围/持续性和已披露量级；明确记录入选理由。没有显著指标变化的事件仍可入选，标记“现有因子未覆盖/抵消/滞后”，不得强行制造对应异常。

先导材料建议从联想已读案例和另外两个已下载期间开始，记录所有审阅文档及其无事件结果，避免只挑成功案例。发现重要事件即登记；不设必须凑够多少条的配额。

每条候选保存以下字段，落在 `docs/evidence/V5.11.csv` 或其配套 JSON 中：

`event_id, company, fiscal_period, period_start, period_end, published_at, discovery_paths, event_type, event_description, selection_reason, affected_metrics, formula_or_query, factor_coverage, document_id, source_location, source_quote, competing_explanations, missing_data, evidence_limits, review_status, method_version, split`

`discovery_paths` 可以是 data、disclosure 或两者；同公司/期间/同一事件合并证据，多原因事件不强行合并为一个原因。先登记数据侧观察，再核对披露，避免把读到的原因假装成由指标独立推出来。候选及待审标签由模型辅助提取可以，正式 gold 必须独立人工确认。

## 步骤 4：先完整做联想 FY2023Q3

直接复用 `data/raw/lenovo/FY23Q3_170220231201.pdf`、`scripts/research_attribution_case.py` 和 `docs/evidence/attribution_case/`；先核对现有来源与计算，不重复编造案例。

1. p2：记录需求疲弱、渠道库存过剩与去库存；公司账面存货和渠道库存分别建证据。管理层解释标注为披露陈述。
2. 数据复算：收入同比约 -24.1469%，期末存货同比约 -11.1297%，但平均余额口径 DIO 从 47.0918 天升至 57.8708 天。核对单位、季度天数、平均库存和单季 COGS。
3. 实现确定性分解：`DIO=平均存货/COGS×天数`，`Δln(DIO)=Δln(平均存货)−Δln(COGS)+Δln(天数)`。仅在正值有效时使用对数；其他情况返回适用性限制或另用明确公式。计算残差并引用输入。
4. p11：入库真实三个月分部收入及抵销；验证 `Δ集团=ΣΔ分部+Δ抵销`。合成 facts_detail 不可替代真实分部，也不可把九个月累计表当单季。
5. p2 的汇率及 CCC 解释单独保存。没有恒定汇率收入/销量/均价，不能定量拆成销量、价格、汇率贡献；管理层 CCC 与项目公式须核对口径。

输出事件候选、推理卡、结构化计算与引用，以及一份 Agent 可读取的披露夹具。上述已知数值用于此开发案例的复核，不写进通用 skill 或隐藏测试答案。

## 步骤 5：将案例提炼为通用推理卡和 skill

每张卡包含：观察模式；候选解释；竞争解释；需要的因子；数学关系；支持证据；反证条件；缺失数据；允许结论；方法版本。

例如“收入下降、存货下降、DIO 上升”：数学上先检查 COGS 是否降得更多；经营上调查需求收缩、库存调整滞后，同时排查备货、并购与口径变化。该模式只能产生调查假设，不能自动证明去库存或需求冲击。

将 `docs/attribution_method_draft.md` 的规则整理进入现有 attribution skill，保留原核验纪律。工作流程为：明确前提与口径→算因子→生成竞争解释→分解/同行比较→检索公开披露→说明支持与矛盾→提交带引用结论。输出区分计算事实、披露解释、推测和无法判断；证据不足允许澄清/拒答。

若现有根因枚举不足，新增“经营事件类型”作为独立维度并登记接口变更；不要把 industry_wide/company_specific 等标签偷换成已证实经营原因。

## 步骤 6：冻结方法，再做泛化验证

发现方法用联想；HP 用作开发验证。冻结 skill、工具、题目和数据版本后，选尚未用于调参的 Dell 期间做公司留出测试。已在案例中查看的 HP FY2023Q1、Dell FY2024Q1 只能作回放/开发材料；不能冒充完全未见的测试。用于修改规则的任何测试案例转入开发集，并另留未查看时期。

独立人工先标注真实事件、允许原因、支持/反驳证据及不确定性，隐藏 gold，加入季节性/无重大事件的阴性对照。被测 Agent 不生成自己的标准答案。冻结 as_of，阻止未来披露与未来重述。

做四组同模型、同预算、同题对照：①数据-only、无新方法；②数据-only、有新方法；③数据+披露、无新方法；④数据+披露、有新方法。每题三次，固定配置并记录运行 ID。开发模型 GLM 5.3 不意味着更改项目运行模型；保持现有 Agnes，除非另获模型切换指示。

报告事件/模式匹配、引用正确率、结论证据支撑、无依据原因、阴性误报、拒答与覆盖率、数值核验、耗时/token/步数。分开评价“数据推理收益”和“读取披露收益”；只做数值回放不能报告经营归因准确率。失败写入 `eval/badcases.md`，改规则后复测开发集，再验证新留出集。
