## 2. 阻断一：补丁式计划修订仍在工具入口失败

位置：`agent/multi.py:415`；`agent/subagents.py` 的 `PlanProposal.validate_semantics()`；现有 `test_w3_revise_only_lists_changed_nodes`。

`save_plan()` 已支持补丁合并，但 `_tool_plan()` 在进入它之前，仍对补丁单独执行 `prop.validate_semantics()`。后者要求每个依赖都存在于**本次 nodes**。因此只改 n2、依赖沿用 n1 的合法补丁，仍得到 `plan_invalid: 依赖 n1 不存在`。

离线复现：先建 n1→n2；mock Planner 只返回修改后的 n2（depends_on=[n1]）；调用真实 `_tool_plan(action=revise)`。实际返回上述错误，latest_revision 仍为 1。现有 W3 测试直接调用 `save_plan()`，绕过出错入口，因此绿色不足以证明 W3 修好。

修法：补丁只验证节点 ID、字段类型、重复项等局部约束；合并后再检查总节点数、依赖存在、自依赖与环。可以由 `save_plan()` 统一负责合并后的语义验证，避免两套互相冲突的校验。

必要回归：走 `_tool_plan()` 或主循环，验证“只改 n2 仍依赖已有 n1”成功且 n1 证据保留；未知依赖和产生环的补丁仍拒绝，失败不改变状态。

## 3. 阻断二：共享预算没有落实到每一次子请求

位置：`agent/multi.py:156,205,379`；`agent/subagents.py:91,149`。

父循环在每个主步骤开始计算一次 `used_tokens`，同一步的多个工具调用继续使用这个旧值；主请求和前一个子调用消耗的 token 没有用于下一次调用的预检。子循环内部每次 `chat()`、以及额外收尾轮之前，也没有检查父级时间/token 预算。子消耗要等整段子循环返回才汇总。

后果：某个 Worker 已经用完全局预算，仍可以继续后续子步骤或收尾请求；同批下一位 Worker 也可能被旧 token 值放行。这与“父子共享预算、耗尽不发新请求”的交付声明不符。

修法：让所有角色的每次模型请求走同一个预算检查与记账入口，包括主请求、子请求、协议纠错和收尾轮；每次返回立即记账。等待 RPM 后、真正发出请求前再次检查时间。已经发出的请求可能造成预算超限，应如实记录；关键是耗尽后不能再发下一次请求。保持主 Agent 自主调度，不引入固定业务顺序。

必要回归：子请求一耗尽 token 后，不发生第二次请求或收尾；同一步批量调用，第一位耗尽后第二位不启动；限速等待跨过时间截止点后不发新请求。用 mock 时钟和 mock LLM，不必联网。

另一个计数缺口：父循环在执行/审查的对象与版本预检之前就递增子调用计数。节点不存在、依赖未完成、已达节点尝试上限等情况会直接返回，实际上没有 `subagent_start`。建议把实际启动计数移至统一启动入口，保持 `subagent_calls == subagent_start` 数量；拒绝单独留痕。

## 4. 修订后的尝试额度需明确处理

位置：`agent/analysis_state.py` 的 `save_plan()`、`mark_stale_downstream()`；`agent/multi.py` 的 `_tool_execute()`。

节点定义变化或下游失效后恢复 pending，但保留 attempt；执行入口却仍按这个 attempt 限制最大两次。离线复现：n1 已完成 attempt=2，再修改其定义，最新节点为 pending、attempt=2，下一次执行会因上限直接拒绝。提示让主 Agent“修订后重做”，实际上可能没有重做额度。

不要盲目把所有计数清零。建议区分“当前节点定义版本的尝试次数”和“全局累计调用次数”，定义变化后给予受全局预算约束的新尝试；或者明确返回此路径已经无额度、需要结束。补测试验证行为与提示一致。
