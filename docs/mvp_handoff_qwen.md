日期：2026-10-02。接收者：Qwen 3.8 Flash 开发执行者。

## 1. 当前目标与停止点

用户当前目标是快速固定一个可运行 MVP，随后亲自参与分析失败案例、讨论通用方法，再由开发执行者实现和复测。现有 plan.md 是完整项目路线；本交接将近期范围收敛为 MVP，不要求把 P6–P8 全部完成才允许用户开始使用。

MVP 要实现：

> 用户输入任意受支持的财务问题 → Agent 选择工具取数、计算，必要时检索公开财报 → 输出带来源的分析结论与限制 → 核验数字和引用 → 保存完整运行记录，供人工讨论 bad case。

停止施工的条件是这条链路可由用户直接运行、结果可检查、失败可复现。准确率不要求达到 100%；已经记录的推理错误进入人工优化阶段。阻止链路运行、错取期间、泄漏标准答案或生成器造错数据等实现缺陷仍须修复。

## 3. 只补 MVP 使用入口与检查材料

### 3.1 一个单问题命令行入口

复用 `agent/v1.py` 的 `run(question, ...)`、现有工具和核验流程，新增轻量 CLI。不要再建一套循环，不需要网页或新 Agent 框架。

建议接口如下（这是待实现命令，README 必须给出最终实际命令）：

```powershell
.venv\Scripts\python -m agent.cli --question "联想 FY2023Q3 存货下降是否意味着周转改善？"
```

- 输入自由文本问题，不依赖预设题号或评测 gold。
- 运行模型继续使用项目当前配置；Qwen 是开发执行模型，不能因此自动切换项目运行模型。
- 复用配置中的限速、预算和错误处理，避免单问题入口绕过免费额度限制。
- 可选 `--as-of YYYY-MM-DD`。若提供，必须用已有快照路由和披露发布时间过滤；仅传日期到 prompt 不构成时点隔离。未提供则明确使用当前数据库，不能称严格历史回测。
- 终端显示结论、status、核验结果、运行 ID 和输出目录。核验失败或预算拒答清楚展示，不能呈现为正常验证成功。
- 核验通过仅说明现有核验覆盖的数字/引用规则通过，不代表经营因果结论已被证明。

### 3.2 自动保存人工可读的运行包

每次运行使用唯一 ID，建议保存在 `runs/<run_id>/`，含：

- `question.json`：原始问题、as_of、可得数据范围。
- `answer.md`：完整结论及引用、核验状态和限制。
- `trace.jsonl`：每步模型可见输出、工具名/参数、结果引用、报错和反馈，以及压缩事件；保留现有 trace 格式。
- `results.json` 或等价可读取存档：本次 ResultStore 的结果、取数 SQL、派生输入和披露出处。人工应能从引用查到数据，只有 rid 名称而没有内容不够。
- `run_meta.json`：模型、脱敏配置、代码 commit/dirty 状态、数据版本/哈希、预算、实际 usage/步数/耗时和必要的披露索引版本。

导出按正常工具返回范围，不无界倾倒整库。API key、环境变量密钥及带密钥的请求头不得进入运行包。

补一个紧凑的人工讨论材料模板：问题、最终结论、预期或争议点、关键工具轨迹、对应证据、当前无法判断的部分。允许人工把该包交给强模型讨论；禁止自动向其他聊天或服务发送。

### 3.3 README 与最小检查

README 写清环境/密钥配置、建库或已有数据要求、单问题命令、输出位置、如何查看引用和 trace、已知失败与数据覆盖。

目前公开披露正文主要覆盖联想。HP/Dell 的财务数字可查，但缺经营披露时必须说明；合成明细不能当真实分部。不要为了 MVP 一次性扩充全部同行语料，需要验证特定事件时再补相应原文。

离线验证 CLI 接线、导出完整性和失败状态；运行现有回归。用少量真实问题检查自由输入链路，包括一个简单取数、一个需要计算的分析、一个需要联想披露的归因。可以复用已有可靠运行证据，但至少一次验证最终 CLI 从用户输入到落盘的真实流程。

另准备 P7.3 的最小鲁棒性检查：不存在/不支持的数据、错误前提、财年/自然年歧义。只验证能拒答、澄清或纠正；如发现失败，区分阻断缺陷与待优化 bad case，不立即扩展成新一轮大型评测。

## 5. 人工主导优化：职责与流程

MVP 收尾后停止自动新增分析规则、自动优化 skill 和新一轮长跑，提交运行命令、输出样例、已知 bad case 清单，等待用户选下一例。

后续每轮：

1. 用户挑真实问题或 bad case，阅读答案及证据。
2. 用户与强模型讨论错误本质和候选修复，形成可组合的通用分析方法及反例。
3. 开发执行者把明确选定的修复落实到工具、提示、skill、核验或上下文管理；记录修改前假设和预期作用。
4. 原题复测，再测相关回归和未参与调参的公司/期间；同模型、同预算控制变量，记录代价及退步。
5. 用户判断是否保留该改进；保存失败尝试，不只展示成功版本。

案例卡属于经验与评测材料，不是一事件一个 skill。200 个事件可以形成 200 条案例，但运行时应使用少量通用分析动作：可比性检查、总量/比率分解、竞争解释、寻找区分证据、时间/同行参照和结论边界。方法保留适用条件与反例，不把 gold 写进 Agent。

“比较同行原始变化率还是 z”目前是待讨论假设，不自动写成必须 z 的规则。要检查基线样本、波动尺度、同一自然期间和真正的业务可比性，再由证据和对照结果决定。

## 6. 面试故事需要保留的证据

每次改进记录：原问题与真实失败 → 如何排除数据/评测缺陷 → 用户提出的分析原则 → 具体 harness 改动与 commit → 原题和新案例结果 → 失败/限制与成本。

后续挑 3–5 个真实经历讲清楚。用户亲自参与的问题判断、方法选择和证据复核应如实记录；自动完成的实现与测试也如实归属。没有做过的实验、泛化效果或人工决策不能补写。
