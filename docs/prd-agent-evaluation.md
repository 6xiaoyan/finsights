# 财务 Agent 三层评测与监控体系 PRD

版本：v1.0；日期：2026-10-16；状态：开发规格，尚未实施。

适用工程：`D:\finsights\finsights-dev`。被测路径优先为 `multi_agent + text2sql`，复用现有 CLI、运行包、ResultStore 和分析状态。

## 1. 目标与边界

本次建设评测与监控体系：保存执行证据，评估端到端结果，分别评估 Planner、Worker、Reviewer，关联 Text2SQL 查询过程，输出可审阅的逐题结果与汇总报告。

本次不以 Agent 分数提升为验收条件。不修改 Agent 的任务拆分策略、角色提示词、查询策略、轮次默认值、审核策略、上下文压缩和调度机制；若缺少观测字段，可以补充事件与导出。发现行为缺陷后登记问题，由后续优化任务处理。

交付形式为本地 Python 模块、CLI、JSON/JSONL 和 Markdown 报告；无需新增 Web 服务、数据库服务、前端、Lenovo 后端集成或自动调优系统。

本 PRD 对评测和监控建设的范围取代 `prd_eval_optimization.md` 中历史阶段限制；旧文档保留为历史记录。真实业务判断、数据来源核验和参考答案隔离规则继续适用。

## 3. 整体架构与实施顺序

```text
真实题目与参考答案、得分点（评测侧）
                 │
题面与批准的业务元数据 ──→ 被测 Agent ──→ 最终答案与完整运行包
                                             │
                                  统一运行包适配与事件关联
                                  ┌──────────┴──────────┐
                             宏观 E2E 评测       中观角色评测
                           得分点＋整篇判断    Planner / Worker / Reviewer
                                                       │
                                                微观查询过程评测
                                            Text2SQL 输入/计划/结果
                                  └──────────┬──────────┘
                                       逐题报告与汇总报告
```

三层使用同一题目、数据版本和运行标识。宏观回答“最终任务完成得怎样”；中观回答“各角色完成职责的质量怎样”；微观回答“具体查询在什么地方偏离目标”。运行错误、耗时和用量单独报告，再与质量结果关联。

实施顺序：先确定公共协议与固定样例，再由 A、B 并行建设；A 内部先做少量完整题目和评分回放，再扩至 30 题；B 内部先做事件与产物关联，再接角色评分。两路完成后进行联合回放、评分校准和少量真实执行验收。Agent 优化另立任务。

## 4. 两个开发 Agent 的职责与文件边界

| 负责人 | 范围 | 建议独占目录 |
|---|---|---|
| Agent A | 真实财报 30 题、参考答案与得分点生成、E2E 评分、数据集审核工具、E2E 报告 | `eval/financial_e2e/`、`eval/datasets/financial_real_v1/`、`docs/eval_e2e_delivery.md` |
| Agent B | 微观事件补充、运行包适配、Planner/Worker/Reviewer 独立评分、过程与角色报告 | `eval/agent_process/`、必要的 `agent/` 埋点修改、`docs/eval_process_delivery.md` |
| 集成审核者 | 公共协议定稿、接口冲突裁定、独立审核与集成 | `eval/contracts/`、本 PRD、集成交付说明 |

以上为建议的新模块位置，不表示这些模块或命令已经存在。公共协议先落到 `eval/contracts/`，A、B 才从同一提交开始开发。B 的适配器返回公共类型；A 不直接依赖 B 的内部实现。已有 `eval/schema.py` 中的 Question/Gold 不适合直接塞入全部新字段，应通过新协议或兼容适配保持旧接口可用。

### 4.1 公共协议先行

至少约定以下数据对象，并提供最小合法与失败样例：

- `CaseInput`：case_id、题面、范围、as_of、业务数据引用。只包含准许进入 Agent 的内容。
- `CaseGold`：case_revision、参考答案、来源、得分点、数值断言、禁止断言、评审状态、数据可见性。仅供评测侧读取。
- `RunArtifact`：run_id、case_id、运行目录、最终状态、最终提交答案及 claims、候选答案引用、版本、过程对象与用量。未成功提交时最终答案字段可以为空。
- `TraceEvent`：schema_version、event_id、run_id、事件类型、开始/结束时间与状态；适用时带 parent_event_id、node_id、plan_revision、角色、role_call_id、tool_call_id、query_trace_id、result_ids、artifact_id 与 artifact_version。
- `GradeResult`：grader 名称与版本、case/run/对象标识、判定、维度分数、证据位置、无法判断的原因、模型与 prompt 版本、用量。

缺失历史字段使用 null，并注明推导来源；不得填 0 冒充已测量。原始参数、查询计划和工具结果保存于运行包；事件可以只存引用与有限预览。评分器按引用读取完整证据，报告展示必要摘要并链接原始证据。

所有评分器均能由固定运行包回放。在线运行缺字段时允许补导出；不得为让历史样例通过而伪造事件。补埋点不得改变工具返回语义或 Agent 可见内容；若不得不改变，应单独列为行为变更并交集成审核。

### 4.2 分支与协作机制

使用两个独立 Git worktree 和分支，例如 `feat/eval-e2e` 与 `feat/eval-process`，禁止两个开发者在同一工作目录切换分支。共享业务数据库只读；临时数据库、运行包和报告分别放到各自目录，避免覆盖。

A、B 各自提交小而完整的变更，交付文件清单、真实可执行命令、样例结果、已知缺口与检查记录。不得擅改对方目录、公共协议或项目全局配置；接口变更先提交具体提议，由集成审核者统一修改公共协议后双方更新。

集成审核者先分别审代码与样例，再在集成分支合并，检查联合回放和既有入口兼容性。开发 Agent 不自行合并 main。分支能合并不等于评测协议正确，必须审核评分公平性、证据引用和参考答案隔离。

## 5. Agent A：30 道真实财报题与参考答案

### 5.1 题目定义与组成

基于港交所公开披露的联想财报，构造并核验共 30 道真实财报问题。直接利用财务报表与管理层讨论、业绩解释和展望设计题目及参考答案，明确标记为“基于财报构造”。不要求寻找公司已经发布的现成问答。

本批限定 Lenovo，使用不同报告期、不同财务变化与业务判断组织题目，无需扩展其他公司或另建多来源搜集流程。优先复用 S01–S07 中符合新协议的案例，计入 30 题并保留来源与审核历史，其余补齐。不能用同一事件简单改写题面凑数。

建议组成：

| 主类型 | 数量 | 重点 |
|---|---:|---|
| 多期比较与财务计算 | 6 | 同比/环比、累计转单季、流量与余额、单位与口径 |
| 变化分解与归因 | 10 | 收入到利润的贡献桥、规模与比率、营运资金联动、替代解释 |
| 证据边界与综合判断 | 8 | 数值与结论的区分、指标改善是否足以支持业务判断、证据冲突 |
| 历史时点预测 | 6 | 固定历史截止日、明确目标与期限、条件与区间、不确定性 |

数量分布可根据实际来源作小幅调整，但须保留预测题、归因题和多步题，交付时说明调整。至少 24 题需要组合多项证据或执行两步以上实质推导；增加无用查询、冗长文字或强行规定节点数不算难度。

每题登记 `reasoning_requirements`，供人工检查复杂度和设计得分点，留在评测侧，不注入 Agent。

### 5.2 来源与可回答性

来源限定为港交所公开披露的联想财报及业绩公告 PDF。优先复用项目已有的原文文件，不足时从港交所补充；无需再从投资者关系网站或其他渠道重复搜集和交叉认证。记录公告标题、港交所 URL、发布日期、报告期、PDF 页码、必要的表格/行列位置及数值单位，保证得分点能够追溯到原文。

每题逐项检查：当前 Agent 能查询到哪些数据、这些数据在什么时间可见、是否包含合成明细、结论能否由可见数据支持。来源核验使用的财报正文可以保存在评测侧；未经明确启用的披露检索不能因此进入 Agent 上下文。

归因题的参考答案优先从财报中的管理层解释提取，再结合报表数字整理为得分点，保留原文与页码。参考答案区分：数字可证明的变化分解、数据支持但不能唯一确定的解释、管理层披露的具体经营原因。当前 Agent 只能查询结构化数字，因此只有可见证据足以支持的内容才列为必答点；只在管理层文字出现的原因保留为参考背景，不要求 Agent 猜中。财报中的管理层解释是可引用的公司说明，不自动等于独立证实的因果事实。

无法由当前工具与数据回答的题登记为 blocked，并记录缺少的指标/期间/披露权限；优先换成可回答的同类题完成正式集。不得为凑齐 30 题临时把标准答案或专用解题步骤送给 Agent，也不把缺数据题混入正常可回答题的通过率。若 30 题不能满足条件，明确报告实际就绪数量和阻塞原因，不宣称数据集完成。

### 5.3 历史时点预测题

每题定义 as_of（当时允许使用的信息截止日）、预测指标、公司、单位、目标期间与预测期限。财报的实际发布日期决定可见性，不能按报告期结束日提前放行。

预测的参考答案包含：截至当时的已知事实、允许的假设、可接受的推理方法、条件和不确定性表述。可参考当时财报的管理层展望并注明来源，但管理层展望不作为必须复述的唯一预测答案。若没有可信的唯一数值预测，不虚构一个“标准预测值”要求语义命中。

后续真实值与其来源单独保存在评测侧，只用于事后误差统计，不进入生成预测的 Agent，也不进入事前推理得分点。运行必须绑定真实的历史快照/可见性过滤；仅在 prompt 写“假设当时”不算隔离。

分开报告预测论证质量与预测结果误差。要求点预测时可统计绝对误差；相对误差必须处理真实值为零及负数的情况。要求区间预测时记录是否覆盖真实值和区间宽度，避免无限宽区间取得虚假优势。六题只能用于逐题观察，不能据此宣称预测能力稳定或已充分校准。

当前 Agent 没有输出题目要求的预测时如实记失败或未完成，不在本次评测建设中新增预测策略。

### 5.4 数据集结构与得分点生成

每题至少保存：case_id、revision、题型、事件分组、题面、业务范围、as_of、数据版本/快照引用、来源、参考答案、得分点、数值断言、禁止断言、可回答性、真实/合成标记、split 与审核状态。

便宜模型根据已核验来源和参考答案生成得分点候选。先完成 3–5 题覆盖不同题型的样本，审核规则后扩至 30 题，避免批量生成后整体返工。

每个得分点包含：稳定 point_id、原子判断、适用条件、required/optional、权重、证据来源、可接受等价表达、矛盾反例、核验方式，以及必要的前提关系。默认必答点等权；业务必须加权时记录理由。得分点不强制对应一句原文，也不要求答案沿用固定段落顺序。

数值断言记录指标、公司、期间、比较基期、数值、单位、方向、公式与接受的舍入精度。区分核心答案数字、可选支持数字和内部自查数字；不要求答案重复全部中间计算。合理替代算法按其条件核验，不强制与参考算法的中间贡献值相同。

逻辑关系用“前提支持结论”的关系表达；只有题目确有展示顺序要求时才检查文字顺序。解释性点写清允许结论与不可断言的内容，不能只是关键词列表。

候选状态为 draft，不得由生成模型自行设 approved。人工或独立审核者完成来源、可回答性、替代答案公平性检查后才能启用正式评分。保留原始候选、修订差异与审核记录。

按共同事件与输入窗口分开发集/留出集，建议约 20/10；若事件关联无法隔离，优先隔离正确并解释实际数量。旧 S01–S07 已作开发用途，继续归开发集。留出题的运行错误分析一旦用于优化，须改记开发用途。

## 6. Agent A：宏观 E2E 评分

### 6.1 评分对象与方法

正式评测对象是实际提交给用户的最终答案及最终状态。候选答案可以做诊断评分，但必须单列，不能替代最终交付成绩。对于应回答题，refuse、异常、轮数耗尽均计入未完成分母；合法澄清/拒答题按该题的预期行为判定。

逐得分点使用 LLM-as-judge：输入问题、参考点、可用事实和最终答案，要求给出答案证据片段、met/partial/missing/contradicted/unknown 与理由。partial 仅在该点有明确部分得分规则时启用。第一版不接 embedding；语义是否等价就在逐点评判中检查。

能取得结构化事实时，程序核验数值、单位、基期、方向和公式；不能可靠抽取时标明使用模型判定，不能声称程序已确认。已有运行时 verifier 结果作为单独诊断字段，不直接替代业务正确性评分。

另一次整篇 Judge 评估扣题、推理连贯、结论与证据一致、条件/不确定性和表达清晰度。每维使用带锚点说明的 1–5 分及证据理由；整篇 Judge 不读取内部 Reviewer 的 accepted/rejected，避免把内部自评当作外部答案。

### 6.2 汇总与异常

输出必答点加权命中率、遗漏点、矛盾点、关键错误、整篇各维得分、最终交付状态、未知项和 Judge 错误。optional 独立展示，不增加必答分母。不得把模型报错、无法判断的点从分母静默剔除；未知点可报告保守/乐观得分区间。

本版不把质量、耗时和 token 拼成一个总分，也不设所有题统一的“80% 即通过”。逐题验收规则来自经审核的必答点、关键错误和预期行为。

Judge 超时、协议错误和缺少证据分别记录，允许显式重评分。重评分产生新版本，不覆盖旧判定。Agent 用量与 Judge 用量、延迟和估算费用分别记录；未知价格记未知，注明费用是估算值还是实际账单。

### 6.3 使用方式

提供三个真实可运行入口，并在交付时给出准确命令：生成得分点候选；对已有运行包评分；按固定数据集调用当前 Agent 并评分。可以采用 `python -m eval.financial_e2e ...`，具体参数在实现中明确。

重评分只读取原运行包，不重新请求被测 Agent。批量执行默认每题一次、低并发；明确区分“对旧答案重评分”和“重新执行 Agent”。保留 code/data/dataset/model/prompt/grader/config 版本，使两次报告能按 case_id 对齐。

## 7. Agent B：微观埋点与运行监控

### 7.1 必须可关联的阶段

记录主循环与每次子 Agent 调用的开始、结束、角色、轮数、终止原因、模型用量；计划修订和依赖；Worker 接到的目标与上游产物版本；Reviewer 审查对象版本、实际读取的证据引用、意见与后续修改；草稿、提交、校验失败与最终终止。

Text2SQL 记录 Worker 发出的自然语言查询、目录/提示版本、提取请求次数及格式修复、QueryPlan、执行参数、结果状态与 rid、data_version、query_trace_id。执行器未产生任意 SQL 时不伪造 SQL 字段。

保存实际交给子 Agent 的可见上下文或可重建的上下文引用清单，用于检查是否遗漏上游信息。区分“数据保存了”“界面展示了”“该次模型实际看到了”。不采集模型私有思维链，不保存 API key。

### 7.2 运行监控指标

提供工具调用成功/失败/跳过数、异常类型、重试、角色调用次数、主/子循环轮数、查询提取次数、结果读取次数、耗时、token 与可获得费用。工具调用成功只描述程序运行状态，不表示取数业务正确。

保留 denominator 与 raw counts，跳过不能计成功，缺少 usage 不能填零。调用事件与子调用嵌套去重，避免客户端事件、主循环转发与子循环事件重复累计。原包字段与重新计算值不一致时同时报告并标记差异。

### 7.3 微观质量诊断

复用既有 Text2SQL 评测资产与接口，补充当前财务场景的可回放输入/计划/结果适配，不另造一套查询工具。

分别检查：Worker 的查询是否符合节点目标；提取器是否忠实表达 Worker 的查询；执行结果是否符合已确认的 QueryPlan。返回表格的列、期间、范围、空值、比较口径与版本均应可核验。目录外问题、歧义澄清、无数据、解析失败和执行失败使用不同原因码。

多写查询次数不自动提高评分，少写也不自动提高评分。质量与调用数量分别展示，后续优化再研究取舍。

## 8. Agent B：中观角色独立评测

每种角色都支持两类输入：固定输入/输出样例的独立评测，以及从真实运行包提取的实际轨迹评测。评分调用在评测侧执行，不把 gold 或评测反馈自动反馈给被测角色。

### 8.1 Planner

输入：问题、Planner 当时可见的业务能力/范围、计划节点和依赖、评测侧得分点。将得分点映射到计划的明确任务范围，区分显式覆盖、合理隐含与未覆盖；映射须给证据理由。

输出：可执行性、依赖合理性、覆盖遗漏、重复任务、范围偏移；同时报告节点数与计划修订次数。节点数不是单独的越小越好得分，不要求固定标准任务图。计划覆盖与最终答案覆盖分开，不能把后续 Worker 补救算成原计划已覆盖。

### 8.2 Worker

输入：节点目标、当时实际获得的上游信息、工具可用能力、查询与结果、Worker 产物及证据引用。

输出：查询意图准确性、取数完整与正确性、结果表结构、计算与结论准确性、证据支持、任务完成度和缺口说明；另列轮数、重试、冗余调用与读取。

区分上游目标错误、上下文交接遗漏、Worker 意图错误、Text2SQL 解析错误、执行器错误与数据不可用；证据不足时允许 unknown，不能仅凭最终错误倒推根因。节点声明 completed 不直接等于任务成功。

### 8.3 Reviewer

固定审核样例包含已标注真实问题和无错误样例，覆盖错期间、单位错误、遗漏、无依据归因、错误引用、合理替代算法及证据不足。输出问题检出、漏检、误报、严重性、证据依据与建议可执行性；有已标注问题时统计 precision/recall 并显示计数。

真实轨迹另关联审查前对象、Reviewer 意见、审查后对象，评估被指出的问题是否修复、是否新引入错误。无法关联版本时不伪造“改进率”。同一问题多轮重复提出应去重并保留轮次。

Reviewer 的 accepted 是被测输出，不是标准答案。修改前后变好只是该轨迹的观察结果；本次不实施 Reviewer 开关对照或因果收益实验，不宣称 Reviewer 已带来能力提升。

## 9. 报告、校准与验收

### 9.1 统一报告

逐题报告按同一 case/run 关联：最终状态与答案、宏观得分点与整篇评分、中观角色结果、微观查询诊断、运行消耗、错误与证据链接。报告直接区分 measured、model_judged、human_reviewed、unknown 的依据。

汇总按题型、真实/合成、开发/留出、数据可用性和配置分组，显示样本数、完成数、失败数与评分错误数。不能把 blocked 题无声消失，也不能将其与已具备输入的正常答错混为一个比例。报告保留原始逐题明细，不只显示总分。

### 9.2 评分校准

先用少量人审答案和固定反例检查评分器：正确等价表达、数值舍入、方向相反、单位错位、条件遗漏、合理替代方法、无依据因果、超长但无效答案、拒答和 Judge 协议错误。

审核错误接受与错误拒绝，修订评分规则并记录版本后再批量评分。生成参考答案的模型与评分模型即便使用相同服务，也必须分开调用、提示和记录；不能把同模型一致当作正确性证明。30 题在审核前只记候选集。

### 9.3 分阶段交付

| 阶段 | 交付 | 验收条件 |
|---|---|---|
| M0 公共协议 | 公共类型、事件命名、合法/失败样例、目录所有权 | A/B 对同一固定样例能读取与输出，无 gold 进入 CaseInput |
| M1 两路最小能力 | A 的 3–5 题样本与 E2E 回放；B 的运行包适配和三角色固定样例 | 逐点证据可追查；角色评分输入独立；失败/unknown 不伪装成功 |
| M2 两路完整交付 | A 的 30 题候选、来源/审核清单和评分工具；B 的埋点、三角色评分与查询诊断 | 核对可回答性、预测隔离、事件关联、接口兼容与得分规则 |
| M3 集成验收 | 统一报告、校准记录、真实命令与交付说明 | 固定包回放可复现；经审核小样本真实执行能贯通；无评分反馈改变被测行为 |

工程检查重点为协议兼容、引用/版本关联、拒答与异常分母、事件去重、参考答案隔离、历史可见性和评分结果保存；使用固定输入和模拟 Judge 避免每次检查都消耗 API。真实 API 调用与本地工程检查分别记录，不使用模拟结果冒充真实评分。

以 `cli-20261016-134035` 回放时，必须同时呈现“节点已完成/内部审查 accepted”和“最终未提交、E2E 未完成”，保留 final_answer 校验反馈及预算终止原因。不得修改原运行包来满足验收。

交付说明写清哪些已实现、哪些仅定义协议、30 题中哪些已审核/阻塞、哪些结果经过人工校准。验收完成只表示评测与监控体系可用，不代表财务 Agent 质量提升或预测能力成立。

## 10. 可直接分派的任务摘要

### 发给 Agent A

依据本 PRD 及已冻结的 `eval/contracts/`，实现 E2E 评测与数据集工具。基于港交所的联想公开财报与业绩公告构造并核验总计 30 题，从报表和管理层解释提取参考答案及得分点，无需扩展来源或寻找现成问答。优先复用合格的 7 道已审开发题，覆盖多期计算、归因、综合判断和历史时点预测，多数需要多步推理。先交付 3–5 题完整样本以校准得分点生成方式，再完成其余候选。记录官方来源与页码，生成参考答案、原子得分点、数值规则、禁止断言和审核状态；预测的未来实绩只留评测侧。实现已有运行包重评分、当前 Agent 数据集运行适配、逐点评分、整篇评分及报告。不得自动批准自己生成的 gold，不改变 Agent 行为，不修改 B 的目录或自行合并 main。交付准确命令、样例和审核/阻塞清单。

### 发给 Agent B

依据本 PRD 及已冻结的 `eval/contracts/`，实现运行包适配、微观埋点、运行监控、Planner/Worker/Reviewer 独立评测与报告。复用现有 trace/results/analysis_state，保存实际可见上下文与证据引用，关联计划/节点/角色调用/工具查询/结果/审查版本。分别评估角色职责质量与查询链路质量，运行成功率、耗时和 token 独立展示；支持固定样例和真实运行包回放。补埋点保持 Agent 行为不变，缺失信息诚实标未知，防重复计数。不得改角色策略、轮次或工具能力，不修改 A 的目录或自行合并 main。交付准确命令、固定包报告、字段兼容表和已知限制。
