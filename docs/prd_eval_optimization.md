# FinSights 评测与优化三阶段 PRD

日期：2026-10-04。接收者：由用户按可用额度选择的开发执行模型。

状态：用户已确认的工作路线，具体实现与结果需按阶段交付。本文件定义近期执行范围；与旧计划、交接文档中关于重复运行、披露检索、提前建设题库和自动优化的要求冲突时，以本文件为准。已有代码与历史实验保留，不把本文件写成已完成成果。

## 1. 背景与目标

项目已存在 Agent 循环、取数与计算工具、单问题 CLI、核验器及运行包导出能力。当前目标不是继续扩展功能，而是让用户能输入一个 query，完整检查结果和执行过程，再亲自参与 bad case 分析、方案裁定与优化。

路线分为三阶段：

```text
第一阶段：单 query 能运行，过程可追查
  → 第二阶段：从公开财报构建归因数据集，人工分析 bad case 并优化
  → 第三阶段：构建历史回测数据集，再优化预测与回测表现
```

当前只执行第一阶段。第一阶段交付后等待用户审阅与推进指令，不自动构建第二、第三阶段的数据集。

## 2. 共同原则

1. 每个 query 在每个版本下运行一次，不要求重复 trials，也不建设稳定性重复跑任务。修改后再次运行属于验证修改，不属于重复抽样。
2. 复用现有 CLI、Agent 循环、ResultStore、核验与导出，不另造一套框架。
3. 用户明确的公司、财年、季度和业务范围由系统映射并落实；存在歧义时澄清，不擅自改范围。
4. Agent 根据结构化财务数据自主分析；经营解释正文不进入本 PRD 定义的被测路径。
5. 公开财报数字可作为业务输入。经营解释文字仅供人工发现事件、构建和审阅参考答案，不能通过工具、上下文、skill 或案例库向被测 Agent 泄漏。
6. 运行轨迹提供审阅证据，不自动等于质量评分。数字核验通过不等于归因正确，SQL 执行成功不等于取数准确。
7. 人工先选择 bad case、判断原因并裁定修改，再由开发执行者实现。不得自动生成并部署推理方法改动。
8. 只用公开与自行合成数据，标明真实与合成边界，运行包不得包含 API key。

## 3. 第一阶段：可运行、可审阅的单 query 底座

### 3.1 用户流程

```text
输入 query（可附明确范围条件）
  → 系统确定并记录范围
  → 按固定规则查询初始结构化数据包
  → Agent 分析，按需补充取数和计算
  → 输出结论、依据与限制
  → 核验并落盘运行包
  → 用户与强模型人工审阅
```

支持 CLI 即可，不要求网页、多 Agent 或新编排框架。开发执行模型由用户按可用额度选择；开发模型与项目实际运行模型是不同配置，不因开发模型变化而自动切换项目运行模型。交付记录中注明实际使用的开发模型与设置（若已知）。

### 3.2 初始输入与补充查询

初始数据包应包括数值及公司、期间、科目、单位、来源、版本、真实/合成标记。记录采用的数据范围规则，不能按参考答案挑选输入。

用户指定范围的过滤由系统执行。数据包覆盖多长历史、包含哪些表或科目，采用一项明确、可配置的规则，并在交付中说明，不要求用户先提供标准答案才能运行。

Agent 可以为分析补取其他指标、历史期间或比较数据。超出用户指定范围的比较要标明用途，不得默默替换分析对象。无真实业务分部数据时，应说明缺口，不能拿合成明细冒充真实经营事实。

现有披露正文检索能力在此路径中禁用，且不得提前注入经营解释。限制应落实到工具暴露或执行层，不能只靠 prompt 要求“不使用”。不要求删除历史语料或旧实验。

若输入 as_of，复用已有时点快照限制可见数据；未提供时明确使用当前数据库，不称为历史回测。

### 3.3 三块审阅视角

| 视角 | 人工要回答的问题 | 必须留下的证据 |
|---|---|---|
| 端到端质量 | 是否回答了问题？数字、分析和结论是否有依据？是否超过数据能支持的范围？ | 原始问题、明确范围、最终答案、claims、数据和计算引用、核验反馈 |
| 取数准确性 | 公司、期间、科目、单位和版本是否正确？查询是否遗漏必要条件？ | 初始数据包及生成查询、每次补充查询的工具参数、SQL（若实际产生）、返回结果和来源 |
| 运行可靠性 | 是否完成或诚实终止？出错后发生了什么？预算花在哪里？ | 工具错误、重试、核验打回、压缩、终止原因、步数、耗时、token 与可获得的限流等待信息 |

不要求展示模型隐藏思维链。保留接口实际返回的可见模型消息、工具调用、证据和最终结论即可。

### 3.4 运行包与可读摘要

优先补齐现有五件套，避免平行建立第二套存储：

| 文件 | 要求 |
|---|---|
| question.json | 原始 query、明确条件、解析后的范围、as_of 和数据包规则 |
| answer.md | 完整答案、引用、状态和核验结果 |
| trace.jsonl | 可见模型输出、工具参数、结果 ID、错误、恢复与压缩事件、终止事件 |
| results.json | 初始数据包和后续工具结果；结果 ID 可关联参数、查询和结果行 |
| run_meta.json | 运行 ID、代码版本及 dirty 状态、数据哈希、运行模型、脱敏配置、预算和实际资源消耗 |

字段可以按现有实现组织，不要求为了字段名大规模重构。重试若在 LLM 客户端内部发生，也应有可追查的事件，不能只保留最终成功调用。

导出有行数上限时必须明确标记截断，并能定位原始结果或重新查询；不能把截断输出称为完整结果。接口未返回的 usage、未知的等待时间或计费信息记为未知，不伪造数值。零价格调用仍记录 token 和耗时。

增加一份人工可读审阅摘要（建议 review.md），关联上述文件。至少列出范围与输入、最终答案位置、工具执行时间线、关键结果引用、错误与终止原因、资源统计，以及三个视角的待人工判断栏。审阅栏默认“未评审”，不得自动标业务 PASS。

运行中出错也保存已获得的轨迹和状态，不能只在正常回答后导出。

### 3.5 第一阶段不做什么

- 不构建任何新评测数据集或标准答案库。
- 不批量运行，不重复 trials，不开发 leaderboard 或 LLM-as-judge。
- 不新增预测任务、回测集或预测模型实验。
- 不自动调 prompt、skill、运行模型、压缩和并行配置。
- 不以修复所有历史 bad case 或完成旧计划全部阶段作为底座交付条件。

阻止运行、范围过滤错误、经营解释泄漏、轨迹丢失等底座缺陷应修复；业务推理错误如实留下供人工讨论。

### 3.6 交付与验收

开发执行者先核对现有功能，提交“已满足 / 需补齐”差异清单，然后仅补齐必要部分。完成后以一个 query 运行一次，例如：

> 联想 FY2023Q3 存货下降是否意味着周转改善？请根据财务数据分析。

此 query 是单次运行验收输入，不要求创建数据集、评分 gold 或专项 benchmark。

交付：实际可用命令、修改说明、输入范围规则、该次运行包、人工可读摘要及已知限制。

底座验收条件：

- query 可输入并完成运行或明确失败；状态与终止原因真实。
- 初始数据范围可检查；被测路径不提供经营解释正文。
- 能从答案引用追到工具结果，再追到参数、查询和来源。
- 取数与计算、错误与恢复、资源与版本信息可以审阅。
- 无 API key 泄漏；真实和合成信息不混淆。

分析是否正确由人工审阅，不把“底座验收通过”写成“归因能力通过”。第一阶段交付后停止扩展，等待用户决定后续工作。

## 4. 第二阶段：财报归因数据集与人工 bad case 优化

### 4.1 目标与启动条件

第一阶段底座经用户审阅可用后，再启动本阶段。目标是把真实财务问题变为可核对的固定案例，并通过人工分析失败原因改进数据分析与归因。

题量与最终评分协议届时裁定，不擅自扩充旧 plan 中的正式题库。

### 4.2 数据集构造方向

1. 从公开财报发现具有代表性的财务变化，核对原始数值和期间。
2. 构造自然的业务问题，固定 Agent 可见的结构化数据。
3. 人工建立关键事实、公式、计算结果及合理结论要点。
4. 审阅“可见数据能推导到哪里”，写明无法确认的解释和禁止断言。
5. 保存来源定位、数据版本与审阅记录，隔离题目输入和参考答案。

财报文字说明真实事件，不等于 Agent 能仅凭数字推导出其唯一原因。数据不可识别的经营原因不能作为强制命中标签。合成已知机制和阴性对照可以补充诊断，但真实和合成成绩分开呈现。

一个案例至少包括：问题及范围、可见数据版本、参考来源、必要事实、计算依据、支持结论、未排除解释、禁止主张及人工审阅记录。

### 4.3 评测与迭代

- 数字、单位、计算和查询结果优先确定性核验。
- 分析结论按人工审阅的要点评分；需要扩展时再引入经过人工校准的 LLM-as-judge，不作为阶段开始的前置工程。
- 每题每版本运行一次，记录逐题结果与原因，不只提供总分。
- 先检查数据、生成器与评分器，再判断是否是 Agent 错误。
- 人工选择 bad case、查看轨迹、讨论方案并裁定一项修改。
- 开发执行模型实现裁定后的修改，在原案例、相关回归案例和未参与修改的保留案例上验证。

开发与保留案例按事件或机制族分隔，避免同一事件的改写题泄漏。若使用“给出正确中间结果”的诊断，其成绩与正常端到端成绩分开记录。

### 4.4 输出与阶段判断

输出：审阅过的归因数据集、评分依据、逐题运行包、bad case 卡、修改前后对比与剩余限制。

用户根据端到端质量、取数准确性和运行可靠性的实际表现，判断是否足够稳定、是否进入第三阶段。当前不预设未经讨论的准确率门槛；不能把题库做出来就称能力达标。

## 5. 第三阶段：回测数据集与预测优化

### 5.1 目标

在前三块能力经用户判断可用后，再构建专门的历史回测数据，接入并优化预测。已有预测代码与离线回测成果保留，但不作为提前启动本阶段的理由。

### 5.2 本轮只确定边界，不确定构造细节

后续另行讨论：公司与指标范围、历史起点、训练长度、预测跨度、时点快照、数据版本、基线、评分聚合和区间评价。此次不指定样本量，不生成回测数据集，不启动预测优化任务。

必须遵守的原则：

- 每个预测时点只使用当时已公开可见的信息，不能用未来值或未来修订数据。
- 未来真实值与 Agent 输入隔离，只用于评分。
- 区分预测工具直接回测与 Agent 使用预测工具的表现。
- 与相同测试点上的明确基线比较，评价点预测误差与区间质量。
- 由人工分析 bad case 并裁定修改，记录改善和退化，而非自动搜索后只报告最优结果。

预期输出：回测数据集及构造说明、基线与预测结果、逐项误差与区间分析、bad case 及修改前后对比。具体验收规则随数据构造方案一起确定。

## 6. 第一阶段开发执行指令

> 请按本 PRD 只执行第一阶段。核对并复用现有单问题 CLI 和五件套运行包，补齐固定范围初始数据、经营解释隔离、可追查的错误与运行记录及人工审阅摘要。输入一个 query 运行一次，提交实际命令、运行包、差异说明与已知限制。不要创建数据集，不要重复 trials，不要自行优化推理方法，不要开展预测与回测。底座交付后等待人工审阅和下一阶段指令。
