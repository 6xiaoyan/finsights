# FinSights：数据来源与数据库设计

整理日期：2026-10-03。本文说明当前项目的数据实现，适合面试介绍与追问准备。最新业务设计以结构化财务数据自主分析为目标：公开财报的经营解释供人工构建和审阅评测案例，不进入目标被测 Agent 的分析输入。现有代码仍有披露检索能力，相关隔离尚需落实；详见同目录《02_评测整体设计与人工优化.md》。

## 1. 一分钟介绍

> 我们从公开财报构建财务分析数据层。联想的数据来自港交所季度业绩公告 PDF，HP 和 Dell 主要来自 SEC 的 companyfacts/XBRL 数据。先抽取数字，统一科目、单位和财季，区分单季度与累计数，再通过财务勾稽关系进行校验。数据写入 DuckDB，事实表保存金额，公司、时间和科目表描述维度，同时保留披露日期、来源和推导方式。目标业务流程是让 Agent 在这个数据层上取数、计算指标，自主验证假设并生成有数据依据的分析结论。
>
> 真实季度总额来自公开财报；当前地区和产品线明细是程序合成的，用于测试筛选和下钻能力。项目没有使用企业内部的一线交易数据，也没有通过机器学习聚类生成财务事实。

这是对项目流程的介绍。个人贡献应按实际参与情况说明，不应把其他开发者完成的工作都说成自己独立实现。

## 2. 数据从哪里来

| 数据部分 | 来源 | 当前处理方式 | 使用边界 |
|---|---|---|---|
| 联想财务数字 | 港交所披露易的季度、半年和全年业绩公告 PDF | 下载原文件，抽取资产负债表与损益表，输出 CSV 后入库 | 公开报表的公司级财务数据 |
| HP、Dell 财务数字 | SEC companyfacts/XBRL JSON | 标准标签映射到统一财务科目，筛选期间并入库 | 部分标签和期间存在缺口，需要检查完整性 |
| 部分缺口与日期修正 | 公开材料的人工核对与补录 | 使用补录 CSV，保留来源与处理记录 | 不是内部数据，也不能将缺失值直接当作零 |
| 地区 × 产品线明细 | 在真实季度总额上自行合成 | 用固定随机种子生成份额，拆分营收、存货和应收，并保证明细加总等于总额 | 不代表公司的真实地区、产品经营情况 |
| 经营解释正文 | 公开财报 PDF 的叙述段和附注 | 按页抽取正文，建立文件索引和检索块 | 目前主要覆盖联想；HP、Dell 的数字可查不等于经营解释正文已完整取得 |

联想的数据路径：

```text
港交所公开公告
  → 原始 PDF + manifest（URL、公告日期、文件 SHA256）
  → 抽取财务科目与数字，生成 CSV
  → 统一单位、科目、财季、期间与版本
  → 财务校验
  → DuckDB
  → Agent 查询、计算与引用
```

披露正文走另一条路径：`公开 PDF → 页级正文块与文件索引 → Agent 检索`。正文主要保存在 `data/disclosures/`，并非整份财报都存入数据库的 `filing_notes` 表。

## 3. 一个真实例子：联想 FY2023Q3 营收入库

### 3.1 原始财报长什么样

原文件：`data/raw/lenovo/FY23Q3_170220231201.pdf`，第 17 页“综合损益表”。下表简化了原表列名，数字保持原值，单位为千美元。

| 科目 | 截至 2022-12-31 本期三个月 | 本期九个月累计 | 上年同期三个月 | 上年同期九个月累计 |
|---|---:|---:|---:|---:|
| 收入 | 15,266,606 | 49,311,761 | 20,126,532 | 54,924,458 |
| 销售成本 | (12,654,361) | (40,954,041) | (16,771,318) | (45,739,744) |
| 毛利 | 2,612,245 | 8,357,720 | 3,355,214 | 9,184,714 |

需要识别的不只是数字，还包括科目、期间、单位和符号。本期三个月与九个月累计同处一行，不能误取累计数作为季度营收；“收入”后面的附注号 `2` 也不是金额。

### 3.2 如何抽取与标准化

`etl/extract_lenovo.py` 使用 `pdfplumber` 读取文本，定位报表页面，根据标签与数值列解析数据。`etl/account_map.yaml` 把报表标签映射到统一科目，例如“收入”对应 `revenue`。

抽取后的 `data/manual/lenovo_income_statement.csv` 中有这条记录：

```text
fy:             FY23
quarter:        Q3
period_end:     2022-12-31
period_type:    3m
line_item_zh:   收入
account_code:   revenue
value_k_usd:    15266606.0
source_pdf:     FY23Q3_170220231201.pdf
```

同一行的九个月累计收入另存为 `period_type=9m`，用于后续第四季度倒算，不直接当成季度事实入库。

`etl/load_db.py` 将千美元统一为百万美元：

```text
15,266,606 ÷ 1,000 = 15,266.606 百万美元
```

对 SEC 的美元数据则除以 1,000,000。成本在原表中以括号表示，项目将 `cogs` 作为正的成本金额存储，再用减法计算毛利。

### 3.3 入库前后检查什么

- 资产是否等于负债加权益。
- 分项与合计是否匹配，毛利是否等于收入减成本。
- 科目映射、季度覆盖和时间序列口径是否连续。
- 是否把全年或累计数误当作单季数。
- 来源、披露日期和派生方式是否有记录。

本例的毛利检查：

```text
15,266.606 − 12,654.361 = 2,612.245 百万美元
```

这些检查帮助发现抽取与口径错误，但单凭勾稽成立不能证明所有数据都正确，更不能证明经营归因正确。

## 4. DuckDB 中的六张表

数据库文件：`data/finsights.duckdb`。以下是当前实际表结构的概括。

| 表 | 作用 | 字段 |
|---|---|---|
| `facts` | 公司季度财务事实，采用一个科目一行的长表 | `company_id, fiscal_year, fiscal_quarter, account_code, value, available_date, version, source, source_ref, derivation, is_derived` |
| `companies` | 公司维度 | `company_id, name, fy_end_month, source` |
| `periods` | 公司对应的财务期间维度 | `company_id, fiscal_year, fiscal_quarter, period_end, calendar_quarter, days` |
| `accounts` | 财务科目维度 | `code, name_zh, name_en, statement, parent_code, is_total, sign` |
| `facts_detail` | 自合成的地区和产品线明细 | `company_id, fiscal_year, fiscal_quarter, account_code, region, product_line, value, synthetic` |
| `filing_notes` | 按公司与财季关联的备注 | `company_id, fiscal_year, fiscal_quarter, note` |

### 4.1 事实表粒度与关联方式

`facts` 的业务粒度是：公司 × 财年 × 财季 × 科目 × 版本。来源、披露日期和推导方式作为附加信息保存。当前表没有声明该组合的唯一约束，因此不能把业务粒度说成已经由数据库主键强制保证。

例如，同一季度的三条真实记录：

| company_id | fiscal_year | fiscal_quarter | account_code | value（百万美元） |
|---|---:|---:|---|---:|
| Lenovo | 2023 | 3 | revenue | 15,266.606 |
| Lenovo | 2023 | 3 | cogs | 12,654.361 |
| Lenovo | 2023 | 3 | gross_profit | 2,612.245 |

关联关系：

```text
facts.company_id                      → companies.company_id
facts.(company_id, fiscal_year,
       fiscal_quarter)                → periods 的对应期间
facts.account_code                    → accounts.code
```

这是事实与维度分离的分析模型；当前代码通过查询关联，没有声明外键约束。`facts_detail` 的地区和产品线目前直接保存在明细行里，没有另建地区、产品线维度表。

### 4.2 为什么用长表

新增一个财务科目通常增加映射和记录即可，无须为每个科目新增数据库列。统一的查询工具可以通过 `account_code` 选择营收、存货、应收等科目，并沿时间查询。

这是灵活性与使用方便程度的取舍：绘制多科目报表时，可能需要透视成宽表；并非所有财务数据库都必须采用长表。

### 4.3 为什么时间维度要带公司

三家公司的财年定义不同，不能仅凭 `FY2023Q3` 就认定属于同一个日历季度。

本例在 `periods` 中是：

```text
company_id:       Lenovo
fiscal_year:      2023
fiscal_quarter:   3
period_end:       2022-12-31
calendar_quarter: 2022Q4
days:             92
```

`days` 还用于周转天数等计算，避免把不同季度都机械地当作 90 天。

### 4.4 为什么保留来源和披露日期

本例营收的追溯字段：

```text
available_date: 2023-02-17
version:        original
source:         lenovo_pdf
source_ref:     FY23Q3_170220231201.pdf
derivation:     NULL
is_derived:     false
```

- `source/source_ref`：回查原始文件或来源记录。本例数据库引用到 PDF 文件名，不是逐单元格的页码定位；第 17 页是此次核对确认的位置。
- `available_date`：判断数据何时公开。本例期末是 2022-12-31，但到 2023-02-17 才披露；历史回测不能提前使用。
- `version`：区分原始与重述数据，避免默认把后续修改后的数值当作当时已知信息。
- `derivation/is_derived`：区分直接报送与程序推导，便于检查计算依据。

典型派生方式包括 `q4_backout`（全年减九个月累计）、`sum_of_parts`（分项相加）、`rev_minus_cogs`（收入减成本）、`residual`（合计减已知分项）等。残差是计算结果，不等于找到了缺失科目的真实独立披露；输入不齐时也不能用零填充后强行计算。

## 5. Agent 如何使用这些数据

用户提问：“联想 FY2023Q3 营收同比下降多少？”

工具查询当前和上年同一财季的原始营收记录：

```sql
SELECT fiscal_year, fiscal_quarter, value, source_ref
FROM facts
WHERE company_id = 'Lenovo'
  AND account_code = 'revenue'
  AND fiscal_quarter = 3
  AND fiscal_year IN (2022, 2023)
  AND version = 'original'
ORDER BY fiscal_year;
```

计算：

```text
同比 = 15,266.606 ÷ 20,126.532 − 1 ≈ −24.15%
```

环比、同比、DIO 等分析指标通常由查询和计算工具基于基础事实生成，不是全部预先存成 `facts` 中的科目。

如果继续问“为什么下降”，需要检索经营披露，并区分数字变化、公司的披露解释与已经验证的因果结论。单靠营收同比不能证明具体原因。

## 6. 和企业 BI 数据流程的区别

| 对比点 | 企业内部 BI 的常见流程 | 当前 FinSights |
|---|---|---|
| 数据起点 | 订单、发票、凭证等业务系统记录 | 已经汇总过的公开财报 |
| 粒度 | 可以细到订单行、客户、产品或法人主体 | 真实数字主要是公司季度科目 |
| 标准化 | 主数据映射、业务规则；部分场景使用分类或聚类 | 财报解析、科目映射、单位与财季统一 |
| 下钻依据 | 真实业务明细 | 当前地区 × 产品线明细为合成数据 |
| 分析入口 | 切片器、报表、指标查询 | 自然语言问题，Agent 调用取数、计算和检索工具 |

不能声称已经还原一线交易数据，或用合成明细证明真实经营原因。项目模拟了部分 BI 分析能力，但没有建设企业完整的上游业务数据链路。

## 7. 面试追问速答

**是不是用 AI 从 PDF 里猜数字？**

当前联想财务数字主要通过 PDF 文本解析、科目规则映射和程序校验取得，模型主要负责后续分析与工具选择。不是让模型凭印象生成财务数字。

**数据是不是全都真实？**

公开报表总额有真实来源，其中部分值经过可追溯的倒算、合并或残差处理；地区与产品线明细是合成的，明确标记 `synthetic=true`，不用于陈述真实分部事实。

**为什么选 DuckDB？**

当前是本地 MVP，数据规模较小，主要需求是 SQL 查询、关联和分析。DuckDB 不需要单独部署数据库服务，便于重建数据与复现实验。这不能直接推导出它就是未来多人生产系统的最终选型。

**最有代表性的数据工程难点是什么？**

不是把数字复制到表里，而是让数字具有可比较的口径：PDF 同行存在单季与累计列、附注号可能被误当金额、不同公司财年不同、单位不同、同一期间可能重述、第四季度可能需要倒算。可以结合自己的实际贡献，从其中一项讲清楚错误现象、定位方法、修复和验证。
