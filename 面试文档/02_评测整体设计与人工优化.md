# FinSights：评测整体设计与人工优化

整理日期：2026-10-03。本文记录与用户确认的评测设计，以及它与现有实现的差异。本文不是已完成的实验报告，不修改现有代码、正式题库规模或验收状态。

## 1. 面试中如何介绍

> 我把评测分为端到端业务评测、补充取数评测、预测评测，以及运行可靠性和效率评测。端到端主要看 Agent 能否根据财务数据得出正确、有依据且不过度推断的结论；取数评测用于定位查询错误；预测通过历史滚动回测评价；系统实验则看质量与耗时、成本的取舍。
>
> 我们用公开财报提取数字，Agent 根据结构化财务数据自主分析，不向它提供管理层对事件的解释。财报文字可以用于人工构建和审阅参考答案，但评分必须考虑：仅凭 Agent 能看到的数据，究竟能合理推出什么。
>
> 优化由人工主导：挑选 bad case，查看运行记录，判断错误原因，与强模型讨论方案，再让开发模型实现一项修改，最后用固定案例和未参与修改的案例检查收益与退化。

这是设计与工作方式的介绍。面试中提到具体提升数字时，必须对应实际完成的实验。已有框架或开发模型完成的实现，不能全部表述为自己独立编写；个人贡献应具体说明案例选择、业务判断、方案裁定和实验分析等实际工作。

## 2. 先确定被测系统的输入边界

### 2.1 用户明确的范围由系统落实

用户已指定的公司、财年、季度、业务范围等条件，应通过结构化参数和明确规则落实到数据库查询，不需要 Agent 再自主决定。自然语言条件仍需要映射到字段；有歧义时澄清，不能静默猜测。

目标流程：

```text
用户问题 + 明确的范围参数
  → 系统按固定规则查询初始数据包
  → Agent 分析并提出待验证假设
  → Agent 按需补充查询、调用计算或预测工具
  → 输出结论、数字来源与不确定性
  → 核验并保存运行记录
```

初始数据包应保留公司、期间、科目、数值、单位、版本、来源和真实/合成标记。其范围规则需要固定并记录，不能按标准答案偷偷挑选数据。若支持历史分析或预测，还要按 available_date 截断当时可见信息。

用户限定业务范围，不意味着 Agent 可以自行改掉范围。额外比较若确有必要，应清楚标注其用途。当前真实公司级季度数据与合成地区、产品明细的边界，也必须对 Agent 和评分侧一致可见。

### 2.2 初始取数与补充取数分开

- 初始取数：系统按用户条件提供约定的数据包，主要验证过滤、映射和数据包内容是否正确。
- 补充取数：Agent 根据分析需要决定还查什么，用于评价自主获取证据的能力。

Text2SQL 只在模型实际生成 SQL 的路径上单独评价。如果补充查询主要使用 query_metric 等固定工具，应评价工具选择和参数是否正确，不必人为增加 SQL 生成步骤。

### 2.3 财报文字属于评测侧材料

目标业务流程不让 Agent 检索管理层的经营解释。公开财报正文可以帮助人工发现事件、审阅参考答案，但不得进入被测 Agent 的初始数据包、工具返回、上下文或案例检索库。

当前代码已有披露检索工具和语料，这是现有能力；把它们从本设计的被测路径隔离，需要后续落实，不能因为本文这样写就宣称已经完成隔离。模型也可能从预训练记忆中知道公开事件，因此真实事件题的得分不能单独证明纯数据推理能力；可补充匿名、扰动或合成对照检查。

## 3. 四类评测，而不是给每个环节都建一个 benchmark

| 对象 | 核心问题 | 数据构造 | 主要评价方式 | 可修改的手段 |
|---|---|---|---|---|
| 端到端分析与归因 | 是否依据可见数据解决业务问题？ | 真实财报案例 + 合成场景 + 阴性或证据不足案例 | 确定性核验 + 按规则的 LLM judge + 人工复核 | 分析方法、语义说明、工具、prompt、skill |
| 补充取数 / Text2SQL | 是否取到了正确的数据？ | 人工查询需求 + 预期结果 + 必要过滤条件 | 结果和业务语义核验 | schema 描述、字段映射、参数约束、查询策略 |
| 预测 | 未来值预测与不确定性是否可靠？ | 按历史可见时点构造滚动回测 | 数值误差、基线比较、区间质量 | 预测模型、方法选择、训练范围与解释 |
| 运行可靠性与效率 | 是否稳定完成，资源投入是否合理？ | 固定业务题 + 长上下文或工具错误条件 | 成功率、稳定性、耗时与资源统计 | 压缩、并行、重试、预算和模型配置 |

问题理解、公式选择、假设验证、结论表达先作为端到端评分维度和 bad case 分类。某类错误反复出现、有明确改进目标时，再构造针对性测试。

Prompt、skill、模型、压缩和并行是优化手段，不是天然独立的业务指标。增加一个 skill 或多调用一次工具，不等于质量提高。

## 4. 端到端分析与归因评测

### 4.1 每个案例保存什么

| 字段 | 用途 |
|---|---|
| question、scope、as_of | 问题、用户明确条件与信息截止时间 |
| 数据库或数据包版本 | 固定 Agent 实际能看到的数据 |
| 来源文件与定位信息 | 人工回查原始财报数字与参考材料 |
| required_facts | 必须正确取得的关键事实、单位和期间 |
| required_calculations | 公式、输入、预期结果和数值容差 |
| supported_conclusions | 可见数据能支持的结论或解释 |
| unresolved_alternatives | 现有数据不能排除的其他解释 |
| must_not_claim | 缺乏依据或与数据矛盾的主张 |
| expected_behavior | 正常回答、合理澄清，或证据不足时限制结论 |
| reviewer、split | 人工审阅记录，以及开发/回归/保留测试用途 |

参考答案以事实和判断要点为主，不要求输出逐字匹配一篇标准文章，也不强制内部思维链。检查可验证的公式、证据和结论即可。

### 4.2 真实事件如何变成题目

1. 从公开财报发现有代表性的变化，核对对应数字。
2. 固定 Agent 可见数据；把经营解释文字放在评分侧。
3. 人工计算必要指标，形成事实和计算标准。
4. 审阅哪些解释可由可见数据支持，哪些不能识别。
5. 按事实、计算、结论与禁止主张建立评分规则。

例：联想 FY2023Q3 存货下降，不等于周转改善。此前核对的可比季度计算中，DIO 由约 47.09 天升至 57.87 天；销售成本下降的影响超过平均存货下降的影响。这可以作为数字和分析判断的参考。具体经营原因则必须根据本题可见数据的范围判断，不能仅因财报文字提到渠道去库存，就要求 Agent 一定说出渠道去库存。

### 4.3 合成场景与真实案例各证明什么

- 合成场景：注入机制已知，适合检查异常识别、变化分解和候选机制区分。
- 真实案例：检查真实口径、数据缺口和多种解释并存时，是否能给出有边界的分析。
- 阴性或证据不足案例：检查是否过度发现异常、编造原因，或者在可以部分回答时过度拒答。

注入标签已知，也不代表机制必然能从输出数据唯一识别。应先检查可识别性；如果两个机制产生不可区分的可见数据，不能强制单一根因答案。场景名和题面也不能暴露注入标签。

### 4.4 如何判分

建议按以下维度输出明细，而不是只有一个总分：

- 关键事实与计算是否正确。
- 是否命中必须回答的分析要点。
- 结论是否由可见数据支持。
- 是否出现 must_not_claim 中的无依据主张。
- 是否合理表达仍不能确定的部分。

数值、单位、公式和查询结果由程序核验；解释和证据支持关系由 judge 按评分规则判断，再人工复核争议项。端到端通过率为“满足预先定义的通过条件的题目数 / 全部被测题目数”。不能只统计成功回答的题目，漏掉运行失败或不当拒答。

可以另外统计关键要点命中比例、无依据主张比例和不当拒答比例，但必须明确各自分母。不能把 judge 的平均评分直接称为事实准确率。

### 4.5 LLM-as-judge 的边界

Judge 获得问题、被测 Agent 的可见数据、参考要点和评分规则，逐项给出判定与依据。财报叙述若提供给 judge，必须注明其仅用于人工参考，不能据此惩罚 Agent 没有推出数据无法支持的隐藏原因。

先用人工标注样本检查 judge 与人工的通过/失败一致性和分歧类型。固定 judge 版本与规则；做成对版本比较时，隐藏版本名并交换答案顺序检查位置影响。数字运算不交给 judge 代替确定性计算。

研究已记录 LLM judge 的位置、篇幅、自偏好和推理能力限制，因此其结果是辅助证据，争议案例仍需人工判断：[Judging LLM-as-a-Judge with MT-Bench and Chatbot Arena](https://arxiv.org/abs/2306.05685)。

## 5. 补充取数与 Text2SQL 评测

人工构造覆盖公司、财季/自然季度、科目、版本、单位、连接、聚合、缺失值和合成标记的查询需求。每题保存需求、预期结果、必要约束及人工核对的参考 SQL 或工具参数。

核心指标：

- 查询结果正确率：结果与标准结果一致的题目比例，按约定处理顺序和浮点容差。
- 业务口径正确率：公司、期间、科目、版本、过滤和聚合符合要求的题目比例。
- 执行成功率：合法且执行成功的查询比例，只作为辅助指标。

不同 SQL 可以得到同样正确的结果，不以 SQL 字符串一致作为主要标准。必要时在替换或扰动后的数据库上复测，避免漏过滤条件、错误连接在当前数据中碰巧得到正确结果。

当前整体 L1 取数题不等于已建立独立 Text2SQL benchmark。只有隔离查询输入与查询输出，才能把查询层的成绩与后续分析成绩分开。

## 6. 预测评测

分成两条线：

1. 预测工具直接回测：评价统计模型本身，不经过 Agent。
2. Agent 预测任务：评价是否选对公司、指标、截止时间、预测跨度和方法，以及是否忠实报告工具输出。

每个截止时点只使用当时已披露的数据。训练期选择方法或参数，未来真实值只用于最终评分；披露日期与报表期间结束日期不能混为一谈。

主要指标是 MAE/MASE、相对 seasonal_naive 的实际回测误差，以及区间覆盖率和宽度。MASE 的分母是训练段季节性朴素预测误差，MASE < 1 不自动等于在测试段打败 seasonal_naive；必须额外比较同一批测试点上的基线误差。覆盖率也要与区间宽度一起看，防止通过无限放宽区间获得高覆盖。

短季度序列下，先评价简单基线和已有模型，不能把少量测试点上的差异宣称为稳定领先。真实案例不足时，合成数据可以检查机制和实现，但其成绩与真实回测分开报告。

## 7. 运行可靠性与效率评测

固定同一组业务题和数据，比较不同配置。统计整体任务通过率、重复运行结果、耗时、token、工具调用次数、限流等待、重试与预算耗尽情况。

- 压缩实验：对比答案与证据是否保留、是否重复取数，以及资源变化。16K 等小窗口是压力条件，与正式配置的成绩分开。
- 并行实验：比较同一限流条件下的耗时和质量；不能把 API 限流等待误认为推理耗时。
- 恢复实验：人为制造可恢复工具错误，观察能否完成；不可恢复错误是否诚实报告。

每项效率修改都同时报告质量，不能只看速度。不存在真实瓶颈时，不必提前展开所有工程实验。

## 8. 评测数据的使用与人工优化闭环

### 8.1 先沿用小规模题库

现有 plan 规定正式评测共 30 题；本文不授权扩大题量。四类评测是组织方式，不是新增四套题库。环节诊断可以复用现有题目和中间结果；确需新增时另行裁定。

开发案例用于讨论和修改；回归案例用于检查已解决问题是否回来；保留测试案例用于检查迁移能力。若同一事件的多个改写题分散到开发和测试中，会形成泄漏，应按事件或机制族分组。小规模拆分无法保证统计显著性，逐例报告结果更诚实。

### 8.2 每轮如何做

1. 人工挑选重要 bad case，保存问题、答案、trace、结果和版本信息。
2. 先核对数据与评分器，排除题库或 harness 错误。
3. 给出错误假设：取数错、计算错、解释过度、记忆丢失等。
4. 必要时提供正确中间结果做诊断，判断错误发生在哪一层。诊断结果与正常端到端分数分开。
5. 人工与强模型讨论方案，选择一个明确修改，再交开发模型实现。
6. 用原案例、相关回归案例和保留案例检查改善与退化；记录资源变化。
7. 根据证据接受或撤回修改，更新 bad case 记录。

每轮实验记录：错误现象、机制假设、具体改动、代码和数据版本、前后逐题结果、过程证据、效率变化和剩余限制。重复跑三次反映随机稳定性，不等于获得三倍独立业务样本。

## 9. 现有实现与后续设计的区别

| 项目 | 当前已存在 | 本文设计仍需落实的部分 |
|---|---|---|
| 端到端评测 | L1/L2 数值评分、L3 合成标签评分、运行报告和 bad case 档案 | 基于可见数据的真实案例参考要点、分析质量评分与人工校准 |
| 查询层 | SQL 工具、指标工具和取数类题目 | 独立补充取数测试与结果/口径判分 |
| 预测 | 预测工具、时点快照、L4 grader 和离线回测 | 后续 live 验证及持续模型实验；不能宣称已完成 |
| 可靠性 | trace、ResultStore、核验器、预算和压缩机制 | 按人工选定瓶颈开展受控对比 |
| 输入流程 | 自由问题驱动工具循环；已有披露检索能力 | 固定范围初始数据包，以及被测路径的经营解释隔离 |

当前 L1 grader 主要检查是否有 claim 数字命中；L3 主要检查标签、科目和工具调用；verifier 主要检查数字出处、引用和勾稽。这些均不等于完整的经营分析质量评测，调用过工具也不代表正确使用了结果。

## 10. 面试追问怎么回答

**为什么不只看端到端分数？**

最终分数能说明产品表现，却难以定位失败。补充取数、预测工具回测和受控诊断可以把问题分开，让修改有针对性。

**为什么不把每个环节都做成独立 benchmark？**

项目规模有限，先保留能形成清晰测试输入、标准结果和改进实验的对象。其他环节先作为评分维度与错误分类，有持续问题再拆出专项评测。

**公开财报是不是给 Agent 泄漏答案？**

数字用于构建数据层；经营解释文字属于人工评测材料，不进入目标被测路径。参考答案也只要求 Agent 达到可见数据能够支持的结论，不能要求猜出不可识别的经营原因。

**你的优化贡献体现在哪里？**

用一个实际完成的案例说明自己如何发现问题、检查 trace、判断机制、裁定方案、分析前后结果和新案例表现。具体实现由谁完成如实说明，不用尚未跑出的提升数字充当成果。
